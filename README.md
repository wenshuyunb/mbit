## 1. 这是什么

SoulMap AI 面向普通微信用户，提供「**认识自己 → 理解关系 → 持续成长**」的闭环：

```
微信授权登录 → 人格测试 → AI 生成个人深度报告 → 分享/邀请伴侣 →
AI 生成关系匹配报告 → AI 情感助手 → 长期人格数据沉淀
```

**商业模式**：免费测试 → 付费深度报告 → 会员 AI 服务（详见 `docs/PROJECT_ARCHITECTURE.md` §1.3）。

### 明确不做（合规红线）

- ❌ 心理疾病诊断、治疗或用药建议 —— 产品定位是**情感成长工具**，不是医疗器械或心理咨询
- ❌ 精神健康危机干预 —— 仅做关怀提示与资源转介
- ❌ 明文保存微信 `session_key`、手机号等敏感信息
- ❌ 面向未成年人的恋爱匹配与付费诱导

所有 AI 生成内容必须附带免责声明，文案由后端 `system_configs` 表下发（全站统一、可热更）。

## 4. 快速开始

> 换机器 / 重装系统后恢复环境、或者用完整离线包（zip）恢复，请看 **`docs/QUICKSTART.md`** ——
> 那份是按真实报错逐条写的，比本节更细（含必填密钥、离线依赖、常见故障排查）。

### 4.1 环境要求

| 工具           | 版本                                           | 说明                                                         |
| -------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| Node.js        | **20 LTS**（后端） / **≥ 22.12**（小程序构建） | uni-app 工具链要求 Node ≥ 22.12；本机 Node 24 可同时满足两者 |
| pnpm           | ≥ 9                                            | 仓库使用 pnpm workspace                                      |
| Docker Desktop | 最新                                           | 用于本地 PostgreSQL 与 Redis                                 |
| 微信开发者工具 | 最新稳定版                                     | 调试小程序                                                   |

### 4.2 启动步骤

```bash
# 1. 安装依赖（monorepo 全量）
pnpm install

# 2. 准备环境变量
cp .env.example .env                 # 按需修改；.env 已被 gitignore
cp .env.example backend/.env         # 后端会优先读取 backend/.env

# 3. 启动基础设施（PostgreSQL 16 + Redis 7）
pnpm infra:up                        # 等价于 docker compose up -d postgres redis
docker compose ps                    # 确认两者 healthy

# 4. 初始化数据库
pnpm db:generate                     # 生成 Prisma Client
pnpm db:migrate                      # 创建并应用迁移
pnpm db:seed                         # 灌入题库、Prompt 模板、商品套餐

# 5. 启动服务
pnpm dev:server                      # 后端 → http://127.0.0.1:3000/api/v1
pnpm dev:admin                       # 管理后台 → http://127.0.0.1:5174
pnpm dev:miniapp                     # 小程序构建（产物 dist/dev/mp-weixin，用开发者工具导入）
```

接口文档（Swagger）：<http://127.0.0.1:3000/api/v1/docs>
健康检查：<http://127.0.0.1:3000/health/ready>

### 4.3 常用命令

| 命令                                           | 说明                                    |
| ---------------------------------------------- | --------------------------------------- |
| `pnpm infra:up` / `infra:down` / `infra:reset` | 启停本地 PG + Redis（reset 会清空数据） |
| `pnpm infra:logs`                              | 查看基础设施日志                        |
| `pnpm build`                                   | 构建后端 + 两个前端                     |

| `pnpm typecheck`                               | 三端类型检查                            |
| `pnpm lint` / `lint:fix`                       | 三端代码检查                            |

| `pnpm db:studio`                               | Prisma Studio 可视化查看数据            |
| `pnpm db:reset`                                | ⚠ 重置数据库（清空数据并重新迁移）      |

**Prompt 模板系统（Phase 3b）**

| 交付物                   | 说明                                                                                                                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **无逻辑模板**           | 占位符仅 `{{name}}`，**不支持 if/for/表达式**。模板由运营在后台编辑，一旦支持分支就等于让他们写一段没有类型检查、没有单测、没有评审的"程序"——分支逻辑应留在可测可 review 的代码里                                |

| **防提示注入**           | 变量值**单次替换**：值里若含 `{{system}}` 不会被二次解析 —— 否则用户可控内容（昵称、报告正文）就能改变 Prompt 结构                                                                                               |
| 正则卫生                 | 每次调用新建 `/g` 正则，绝不复用模块级实例（带 `g` 的 RegExp 携带可变 `lastIndex`，混用 `replace`/`matchAll` 会产生"第二次少匹配"的间歇性 bug）                                                                  |
| **版本分流（AB）**       | `activeVersionId` 显式钉版优先（灰度回滚只需把指针指回上一版）；否则在多个 `ACTIVE` 版本间按 `trafficWeight` 加权选择，随机源可注入以便确定性测试                                                                |
| 两处退化兜底             | 权重全为 0 时**退化为等权**（全零点通常是编辑中间态，选不出会让线上报告生成整体失败）；`random()` 返回 1（闭区间实现）时仍返回末位版本而非 `undefined`                                                           |
| **缓存策略**             | 按 `versionId` 缓存版本内容（版本一经发布不可变，因此**永不需要失效**，发新版自然产生新键）；「哪个版本生效」的指针查询**不缓存** —— 缓存它会造成"后台改了 prompt 但线上仍用旧版"，而热更正是 ADR-014 的核心诉求 |
| 脏数据容错               | 钉住的版本查不到时**回落**到按状态选择（脏指针不应让报告生成整体不可用）；缓存结构不完整时重新查库（不让 `undefined` 流到渲染层）                                                                                |
| 测试                     | **新增 34 个（合计 925 个 / 33 个套件）**：渲染 14 个（含二次替换防护、JSON 花括号）、分流 7 个（含两处边界）、服务 13 个（钉版/回落/缓存/失效）                                                                 |

**报告生成编排（Phase 3d-2）**

把 Phase 3 的三块基础设施串成流水线：上下文组装（3c）→ Prompt 模板（3b）→ Provider（3a）→ 分段解析（3d-1）→ 落库。

| 交付物                          | 说明                                                                                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **幂等 = 不为同一内容付两次费** | 同画像 + 同 Prompt 版本 + 同模型 → 报告必然相同，因此已 `SUCCEEDED` 的报告**直接复用，不再调用模型**。用户连点两次、队列重试都不会重复付费 |
| **重新生成先清空旧分段**        | 段落键虽稳定，但「本次没产出的段落」必须消失 —— 否则上一版残留内容会混进新报告（有测试断言删除发生在写入之前）                             |
| **失败也记账**                  | 失败的调用同样消耗 token（输出格式非法、内容截断）。只在成功时写用量日志会让成本看板**系统性低估**，而看板的用途正是发现异常               |
| **不落库空报告**                | 模型返回空内容、或全部段落都无正文时判为失败（`50004`），而不是存一条空报告让用户白等                                                      |
| 确定性带来的简化                | 生成时**重新推导**上下文与 Prompt 而非落库变量快照 —— 3c 的确定性保证"重新推导 = 首次推导"，因此少维护一份可能与画像脱节的数据             |
| 失败语义                        | 报告标记 `FAILED` + `errorCode`/`errorMessage`（截断 1000 字符）后抛出，交由队列重试策略处理                                               |
| 记账容错                        | 写用量日志失败**不影响**已成功的报告（报告已落库，日志事后可补）；无 token 数据时（调用未成功返回）不写日志，避免记一条 0 消耗的噪声记录   |
| 测试                            | **新增 19 个（合计 984 个 / 36 个套件）**：成功路径 6 个 + 幂等 3 个 + 重新生成 1 个 + 失败语义 7 个 + Provider 选择 2 个                  |

**按段裁剪（Phase 3d-3，ADR-004 的安全核心）**

| 交付物               | 说明                                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **正文不下发**       | 未解锁段落的 `content` 为 `null`，**且可见性类型里没有任何字段能承载正文** —— 想泄露付费内容必须主动新增字段，而不是「忘了过滤」就会泄露 |
| 为什么不能靠前端隐藏 | 把全文发给前端再隐藏有两个致命问题：① 抓包即可看到全文；② 前端一旦有 bug 或改了渲染逻辑，付费内容直接暴露                                |
| **不发片段**         | 连「前 N 字试读」也不做 —— 那是内容泄露向量。契约的模型是「免费**段**」而非「免费片段」                                                  |
| 只暴露体量           | 未解锁段落仍下发 `contentLength`（便于展示「解锁可读 N 字」），长度不是内容                                                              |
| 免费段永远可见       | `isFreePreview` 为真的段落不受解锁状态影响 —— 这是 ADR-004 给用户的最低保证                                                              |
| 空报告不视为全解锁   | 空集合时 `isFullyUnlocked` 为假（否则「零段落」会被误判为「全部可读」）                                                                  |
| 显式失败而非空壳     | 一段都不可读时抛 `50019`（需解锁），报告无任何段落时抛 `50016`（配置事故）—— 都不下发空壳报告让用户以为报告坏了                          |
| 顺序与纯度           | 以 `order` 为准排序（不信任入参顺序），且不修改入参数组                                                                                  |
| 测试                 | **新增 18 个（合计 1002 个 / 37 个套件）**：可见性 12 个 + 汇总 3 个 + 断言 3 个；其中 3 条直接对**序列化结果**断言不含付费正文          |

**CompatibilityEngine（Phase 4a）**

| 交付物                 | 说明                                                                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **MBTI 互补性**        | 不把同/异极当二元判断，而是按**偏好强度插值**：`中性分 + (基准分 − 中性分) × 平均强度`。双方都在 50 附近时该维度信号很弱，分数收敛到中性 —— 而不是因为"异极"就扣分 |
| **大五配置化**         | 每特质声明 `SIMILAR`（越接近越好）或 `COMPLEMENTARY`（差异接近 `idealGap` 最好，如外向性差 20 分互补、差 60 分生活节奏难同步），并带子项权重                       |

| 沟通偏好               | 爱的语言共享数计分 + 冲突风格一致性（相同优于不同，但不同不是低分 —— 只是沟通成本更高）                                                                            |
| **缺数据重新归一权重** | 某维度缺失时剔除该子项并把其余权重**按比例放大**，总分仍在 0–100。按 0 分计入会把"没测"表达成"关系很差"，是错误结论；`skippedDimensions` 如实列出被剔除项          |
| 无依据即失败           | 有效权重全为 0 时抛 `50004` —— "无依据的匹配度 65 分"比明确报错更有害                                                                                              |
| **可解释性**           | `scoreBreakdown` 含权重版本、引擎版本、**实际生效权重**（归一后）与逐维度明细，前端可画拆解图、客服可回答"为什么是 72 分"                                          |

**邀请闭环基础（Phase 4c）**

| 交付物                 | 说明                                                                                                                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`pairKey` 顺序无关** | 按字典序拼接两端 id。**排序是全部意义所在**：`A:B` 与 `B:A` 必须是同一个键，否则同一对用户能建出两条关系，`UNIQUE(pairKey)`（ADR-020）完全失效                                                              |
| 自关系拒绝             | 自己与自己建立关系在业务上无意义，且会让「我与我匹配」成为可能                                                                                                                                              |
| `pairKeyIncludes`      | 供关系详情页判断权限；非法键返回 `false` 而非抛错（权限判断不该因脏数据崩溃）                                                                                                                               |
| **Crockford Base32**   | 邀请码要**被用户念出来、手输、认出来**。Crockford 去掉了易混淆的 `I`/`L`/`O`/`U`，并约定解码时 `I`/`L`→`1`、`O`→`0` —— 标准 Base32 保留 `I`/`O`，用户看到 `O` 念"零"、看到 `I` 念"一"，是客服工单的常见来源 |
| **密码学随机源**       | 用 `crypto.randomInt` 而非 `Math.random`：后者可预测，攻击者能通过已发放的码推算后续码、**猜中他人邀请码并抢先接受**（邀请码本质是 7 天有效的临时凭证）                                                     |
| 输入容错               | 归一化处理小写、空格、连字符（用户习惯四位一断）与混淆字符，避免「用户坚信自己输对了但系统说无效」这类无法自查的工单                                                                                        |

**邀请状态机（Phase 4d）**

| 交付物                 | 说明                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createInvite`         | 生成短码（DB + Redis 双写）、7 天有效期、限制同时未使用邀请数 ≤ 5                                                                                                                  |
| **码碰撞重试**         | `code` 有唯一约束，32^8 空间里碰撞是**正常概率事件** → 重试生成而非报错。抛错会让用户看到"生成失败请重试"，而系统完全有能力自己解决；连续 5 次碰撞才抛 `90000`（码空间异常需暴露） |
| **Redis 只是加速层**   | 写缓存失败**不回滚业务**（扫码时会回落到 DB 查询），因此只记警告不抛错                                                                                                             |

| **幂等接受**           | 重复接受同一邀请返回既有关系而非报错；邀请已接受但关系记录消失时抛"已被使用"                                                                                                       |
| **`pairKey` 唯一闸门** | 并发接受、两人互相邀请等场景下，唯一约束会拦住重复关系。这是**正确的拒绝**，归一为 `60002`（关系已存在）而不是 500 —— 应用层"先查再插"在并发下必然漏判                             |
| 对方需有画像           | 无画像则无法算分，匹配报告无从生成 → `60009`（同伴尚未就绪）                                                                                                                       |
| 测试                   | **新增 21 个（合计 1129 个 / 44 个套件）**：创建 8 个（含碰撞重试与上限）+ 接受 13 个（含幂等、自邀、越权闸门、事务边界）                                                          |

两阶段管道（与 Prisma `CompatibilityReportStatus` 枚举一致）：`QUEUED` → `COMPUTING` → `SUCCEEDED`。枚举里的 `GENERATING` 是为**第二阶段（AI 解读）**预留的。

| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `CompatibilityService`              | 触发（幂等 + 缓存命中复用）、算分落库（`$transaction` 同时更新关系表的 `lastReportAt`/`reportCount`）、查询                                                          |

| **确认时自动触发**                  | 契约 §3.6.6 的 `autoGenerateReport`。**入队失败绝不回滚激活**：关系已生效是既成事实，回滚会让用户「确认了却没确认上」。失败如实返回 `enqueued: false` + `skipReason` |

| **阻断原因顺序**                    | 先判关系状态 → 再判「我」→ 再判对方。「我还没测」优先于「对方没测」：顺序反了会让用户去催对方，而问题在自己这边，白等一轮                                            |
| **`canGenerate` 用同一份规则**      | 列表/详情的 `canGenerate` 与触发接口共用 `resolveCompatibilityBlocker` —— 否则会出现「列表说可以生成、点进去报不能生成」这种自相矛盾的界面                           |
| 失败必须落库                        | 只打日志的话用户永远停在「生成中」，列表页也无法告诉他「这份失败了、可以重试」。失败文案对客户端只用**友好文案**，不透出引擎/SQL 原文                                |
| **`import type` 陷阱**              | 构造参数注入 `CompatibilityService` 必须用普通 `import`：`import type` 会被编译期擦除，Nest 的 `design:paramtypes` 拿不到运行时类引用，注入会**静默失败**            |
| 测试                                | 后端 **1254 个 / 49 个套件**（新增 15 个：`cacheKey` 与 blocker 纯逻辑 14 + 路由契约 1）                                                                             |

**关系报告模板与上下文（Phase 4i）**

匹配报告的**第二段（AI 解读）**的准备。算分结果已在库里，但 `advantages` / `conflicts` / `suggestions` 三个 JsonB 列仍为空——它们由这一段的输出填充。

| 交付物                                   | 说明                                                                                                                                                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `relationship-report-context.builder.ts` | 为关系报告组装 Prompt 变量：双方 MBTI/四维/大五/依恋/爱的语言/冲突风格 + 算分总分与分项 + 分项明细 + 被跳过的维度                                                   |
| **为什么与单画像构建器分开**             | 硬塞进同一个函数会让「哪些变量该有值」变成一串条件分支，且 `unavailable` 判定互相污染——单画像里「爱的语言不可用」在关系报告里可能是「只有一方不可用」               |
| **视角前缀 `my*` / `partner*`**          | 报告是给当前用户看的，而算分输入是 A（邀请方）/ B（接受方）。若 `my*` 填了 A 的数据，B 阅读时报告会把对方说成「你」。测试专门断言「交换 me/partner 后视角整体对调」 |
| `report.relationship` 模板               | 4 段式：契合优势（免费预览）/ 潜在分歧 / 相处建议 / 沟通话术示例。段落键与 `compatibility_reports` 的列一一对应                                                     |
| **段落键必须等于数据库列名**             | 键写错时内容被塞进兜底键 `extra-{n}`，对应列永远 NULL——表现为「报告生成了但优势/冲突是空的」，且**不报任何错**。已用测试把键名与列名钉在一起                        |
| 只在 Prompt 里放有用的东西               | 分项明细只提取「有分数且 `counted: true`」的维度并附权重；内层 `breakdown` 结构与应用权重元数据都不进 Prompt（浪费 token 且是噪声）                                 |
| 复用而非复制标签映射                     | 从 `report-context.builder.ts` 导出 `ATTACHMENT_LABELS` / `describeDimension` 等 8 个共享件，避免同一份标签表维护两处                                               |
| 跨模块契约测试按模板路由                 | 原来的占位符测试统一用单画像构建器校验；关系模板引入后必须**按模板键路由**到对应构建器——否则要么误报失败，要么把两套变量并集成大集合、笔误再也测不出来              |
| 测试                                     | 后端 **1272 个 / 50 个套件**（新增 18 个：上下文构建 16 + 模板契约 2）                                                                                              |

**匹配报告 AI 解读接线（Phase 4j）**

至此匹配报告两段管道打通：`QUEUED → COMPUTING →（算分落库）→ 触发解读 → SUCCEEDED`。

| 交付物                                   | 说明                                                                                                                                                                    |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ReportService.createRelationshipReport` | 关系报告走**独立取数路径**：不挂画像（`profileId` 为 null），改挂 `relationshipId`；生成时读双方画像 + 算分报告                                                         |
| **`cacheKey` 用算分报告 ID**             | 算分报告本身已由「双方画像版本 + 权重版本 + 引擎版本」决定（`buildCompatibilityCacheKey`），复用它就自动获得同样的确定性，不必再拼一遍                                  |
| **必须有已成功的算分报告**               | 没有分数就没有可解读的内容。此处**不能**退化成让 AI 自己编一个分数——那违反 ADR-005（算分确定、AI 只解读）                                                               |
| 反向关联 `aiReportId`                    | 创建解读后回写 `CompatibilityReport.aiReportId`；生成完成时正是凭这个关系把分段回写到三个 JsonB 列                                                                      |
| **`relationship` → `ai` 单向依赖**       | `AiModule` 不反向依赖关系域（报告生成只用到 `relationship-view.util.ts` 的纯函数，不是模块）。不走队列而直接调用：这段编排很短，且失败必须能被算分流程感知并降级        |
| **解读入队失败不影响算分**               | 算分是确定性事实且已落库，解读只是叙述层。失败只记警告——否则用户会看到「匹配失败」，而分数其实已经算好了                                                                |
| **段落键 → 列名的一次映射**              | 不靠段序猜（模型少写一段时段序必然错位）。缺段时显式写 `Prisma.DbNull` 而不是「不更新该字段」——后者会让重生成时旧内容混进新报告                                         |
| **发现并修掉的数据缺口**                 | 模板原本设计 4 段（含「沟通话术示例」），但表里只有 3 个 JsonB 列——那段内容生成出来后**静默丢失**。改为 3 段，把话术要求并入建议段                                      |
| **`undefined !== null` 陷阱**            | 判定"是否为关系报告"时用 `typeof === 'string'`。`undefined !== null` 为**真**，于是没有该字段的对象（测试替身、旧数据）会被误判成关系报告——这个错误当场让 16 个测试失败 |
| 测试                                     | 后端 **1272 个 / 50 个套件**（本轮为接线，未新增用例；修掉了 `prepareForRelationship` 与事务替身带来的回归）                                                            |

**权益体系（Phase 6a）**

此前 `ReportController` 里的解锁状态是一个恒返回「全锁」的桩，付了费也打不开付费墙。本轮把它换成了真实的权益判定。

| 交付物                             | 说明                                                                                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `entitlement.util.ts`              | 纯逻辑：资源键编解码、权益有效性、报告解锁判定、会员判定。**28 个单测**                                                                       |
| `EntitlementService`               | 只负责取数（一次查完该用户全部权益，避免按报告 N+1）；判定全部委托给纯函数                                                                    |
| **`resourceKey` 编码约定**         | `report:{reportId}`（整份）/ `report:{reportId}#{sectionKey}`（单段）。约定写在一处 —— 编码与解码必须成对演进                                 |
| **`CONSUMED` 仍算已解锁**          | 一次性权益"用掉"后状态变 `CONSUMED`，但用户买的是**内容访问权**，不是"一次查看"。判为无效会让用户刷新一次报告就又被挡住                       |
| **`expireAt` 为 null ≠ 已过期**    | null 表示永不过期。缺失时按"已过期"处理是常见误写                                                                                             |
| **会员优先于单份购买**             | 否则会员看到的解锁来源是 `REPORT_PURCHASE`，前端可能显示"你已购买本报告"，让用户以为自己付了两次钱                                            |
| **缺 `expireAt` 的会员按无效处理** | 否则一条脏数据等于白送终身会员                                                                                                                |
| **两种整份解锁写法都要认**         | `reportId` 外键与 `resourceKey` 通用键历史上都在用；只认一种会出现"权益在库里但用户看不到"                                                    |
| **脏数据跳过而非抛错**             | 解析失败返回 `null`：一条旧格式数据不该让整页 500，最多少解锁一段                                                                             |
| 已解锁数用权益侧批量统计           | 摘要里的 `unlockedReports` 不按当前页外推，保证与列表项 `isUnlocked` 同一口径                                                                 |
| **私有方法会被路由契约测试抓到**   | `resolveUnlockStateFor` 原为控制器私有方法，被"恰好 N 个路由"的断言当成新增路由。移到模块级函数，而不是加排除名单 —— 后者会让断言失去防护作用 |
| 测试                               | 后端 **1300 个 / 51 个套件**（新增 28 个权益判定用例）                                                                                        |

**微信支付回调核心（Phase 6b）**

本轮做的是支付链路里**最安全敏感**的一段：验签、解密、发货判定。全部为纯函数，**测试使用真实 RSA 签名与 AES-256-GCM 往返**（不用桩——这类代码的价值就是"算得对"，用桩测等于把公式抄一遍再断言自己抄对了）。

| 交付物                                | 说明                                                                                                                                                                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `wechat-pay-crypto.util.ts`           | RSA-SHA256 验签、时间戳新鲜度、AES-256-GCM 解密、常量时间比较。**23 个单测**                                                                                                                                 |
| `payment-notification.util.ts`        | 通知解析（商户号/状态/金额/币种）与发货判定（幂等、终态）。**21 个单测**                                                                                                                                     |
| **为什么单独成文件**                  | 项目里现在有**三套**互不兼容的算法：自有字段 AES-256-GCM（`CRYPTO_KEY`）、微信登录 AES-128-CBC（`session_key`）、**微信支付 AES-256-GCM（`apiV3Key`）**。混在一处最典型的误用是拿 `session_key` 去解支付回调 |
| **先验签、再解密、最后用字段**        | 顺序反过来，攻击者可以用自己生成的密钥构造"已支付"的密文体 —— 服务端解密成功并发放权益。这是支付系统最经典的漏洞                                                                                             |
| **时间戳必须双向校验**                | 只验签不校时间的话，攻击者能重放一个曾合法的旧回调（签名依然正确）。只判"太旧"也不够：服务器时钟被校正到未来时会放行一批未来时间戳                                                                           |
| **认证标签在密文末尾**                | 微信把 GCM 的 tag（16 字节）直接拼在 `ciphertext` 末尾，不像标准分字段传输。忘记切分就会把 tag 当密文解出多余字节                                                                                            |
| **`apiV3Key` 与 nonce 是 ASCII 直取** | 不是 base64 解码 —— 32 个可见字符的字符串本身作为密钥                                                                                                                                                        |
| **必须核对商户号**                    | 攻击者可把自己订单的真实回调重放到我们的服务：验签能过（确实是微信签的），但商户号不是我们的                                                                                                                 |
| **金额必须与订单应付额相等**          | 只判"回调金额 ≥ 应付额"不够：少付是资损，多付意味着串单，两者都必须暴露而非静默按应付额发货。**记账一律用订单侧的 `paidAmount`，回调金额只用于比对**                                                         |
| 商户号校验收在状态校验之前            | 顺序反了会把"发给别人的通知"报成"交易未成功"，掩盖更重要的事实                                                                                                                                               |
| **幂等键用订单号而非交易号**          | `entitlements.idempotencyKey` 有唯一约束，是数据库层的防重闸门（比"先查再插"可靠，并发下只会放行一条）。用交易号反而会让同订单的第二次通知生成不同的键                                                       |
| 测试                                  | 后端 **1344 个 / 53 个套件**（新增 44 个）                                                                                                                                                                   |
| **尚未接线**                          | 回调 HTTP 入口、订单查找、`Order` 状态流转与权益发放事务、下单接口 —— 见「已知未完成项」                                                                                                                     |

**支付回调接线（Phase 6c）**

至此「微信通知 → 订单已付 → 权益落库 → 付费墙打开」这条链路打通（`POST /payment/notify/wechat`）。

| 交付物                        | 说明                                                                                                                                                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WechatPayService`（infra）   | 验签 + 解密，**不涉及订单与权益**。平台证书读文件并比对内容缓存 —— 轮换时自动刷新（缓存"读过没有"会导致轮换后所有回调失败且难以定位）                                                                      |
| `PaymentService`              | 通知 → 订单状态流转 → 权益发放，**同一事务**                                                                                                                                                               |
| `POST /payment/notify/wechat` | `@Public` + `@RawResponse` + `@SkipThrottle({global:true})`（微信出口 IP 集中，按 IP 限流会在支付高峰误伤回调）                                                                                            |
| **必须用原始请求体验签**      | 不能用 `JSON.stringify(body)`：重新序列化会改变空白与键顺序，签名字节不一致 → 永远验签失败。因此 `main.ts` 开了 `rawBody: true`                                                                            |
| **双闸门幂等**                | ① `decideFulfillment` 的订单状态判断 ② `entitlements.idempotencyKey` 唯一约束 + `order.updateMany` 带状态条件。只有 ① 时并发下会双双发货；只有 ② 时订单状态与权益可能不一致                                |
| **何时回成功**                | 重复通知回成功（否则微信持续重投）；**确定性拒绝也回成功**（订单不存在、金额不符，重投结果相同）；验签失败与内部异常**不回成功**（前者可能是攻击或证书过期，后者需要微信重投兜底）                         |
| 会员到期从**付款时刻**起算    | 从下单时间算的话，用户等一天再付款会白扣一天                                                                                                                                                               |
| 未知商品类型不发默认权益      | 发错权益比不发更糟（用户以为买到了会员）。保持「订单已付、权益待补」并告警，由补单脚本处理                                                                                                                 |
| **发现并修掉的真实缺陷**      | `decideFulfillment` 里写了 `EXPIRED` —— 这个状态**并不存在**（真实枚举是 `CLOSED`）。那条分支永远不会命中，超时关单的订单会被当成待支付而发货。已收紧成联合类型 `OrderStatusValue`，让这类错误编译期即失败 |
| 测试                          | 后端 **1345 个 / 53 个套件**                                                                                                                                                                               |
| **仍未实现**                  | 退款与退款回调、平台证书自动下载轮换、订单超时关闭与对账                                                                                                                                                   |

## 7. 开发原则（强制）

1. **先设计，再编码** —— 接口未在 `API_DESIGN.md` 中定义，不写 Controller
2. **每个模块必须带测试** —— 业务代码与测试同一次提交；核心算法覆盖率 ≥ 95%
3. **禁止一次生成大量代码** —— 单次提交聚焦单一模块（≤ 800 行有效代码）
4. **禁止删除已有稳定代码** —— 重构必须保持测试全绿
5. **核心业务必须有数据库记录** —— 无落库的业务视为未完成
6. **所有 AI 输出必须保存** —— `ai_messages` / `ai_reports` / `ai_usage_logs` 强制写入
7. **所有接口必须有 Swagger 文档**
8. **所有配置必须走环境变量** —— 缺失即启动失败，禁止带病启动
9. **禁止把 Key 写入代码** —— `.env` 已 gitignore，CI 用 gitleaks 扫描
10. **代码必须达到商业上线标准** —— 见架构文档第 18.3 节质量门禁

补充的工程约定：

- **金额只用整数分**，字段名以 `Amount` 结尾（浮点误差是支付事故级问题）
- **主键统一 UUIDv7**（时间有序、索引友好、不泄露业务规模）
- **错误码禁止硬编码数字**，必须引用枚举
- **AI 调用只能发生在 `ai` 模块内**，其他模块通过 `AiService` 出口
- **算法必须是纯函数**（人格算分、匹配算分）—— 无 I/O、可 100% 单测、结果可复现
- **前端不得信任服务端下发的全量内容后自行裁剪** —— 付费内容由服务端裁剪段落

```

> **本机 `docker compose` 子命令不可用时的替代方案**
>
> `docker-compose.exe` 已安装在 `C:\Program Files\Docker\cli-plugins\`，
> 但本机 Docker CLI 未发现该插件目录（`docker compose version` 报 `unknown command`）。
> 有两种解决方式，任选其一：
>
> 1. **启动 Docker Desktop 后重试** —— Docker Desktop 启动时会自行配置好插件路径，通常即可恢复；
> 2. **直接调用二进制**（已验证可用）：
>    ```powershell
>    & "C:\Program Files\Docker\cli-plugins\docker-compose.exe" -f docker-compose.yml up -d postgres redis
>    ```
>
> 也可以把上面这行封装成自己的别名。无论哪种方式，编排文件本身无需改动。

编排设计要点（已通过配置评审）：

- 端口仅绑定 `127.0.0.1`，不暴露到局域网

- Redis 7-alpine（`appendonly yes`；`maxmemory-policy noeviction` —— **保证 BullMQ 队列消息不被淘汰**）

- `adminer` / `redis-commander` 放在 `tools` profile 下，默认不启动：

**下单接口（Phase 6d）**

至此「下单 → 拉起支付 → 微信通知 → 权益落库 → 付费墙打开」全链路可用。

| 交付物                      | 说明                                                                                                                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wechat-pay-sign.util.ts`   | 商户侧签名：请求 `Authorization` 头、小程序 `paySign`、PEM 换行还原。**25 个单测，全部真实 RSA 签名往返**                                                                              |
| `order.util.ts`             | 订单号生成、金额校验、商品快照、过期时间、客户端 IP 归一                                                                                                                               |
| `POST /payment/orders`      | 创建订单 + JSAPI 预支付 + 返回 `wx.requestPayment` 可直接使用的参数                                                                                                                    |
| **三处待签名字符串的差异**  | 请求头 `mchid\nnonce_str\ntimestamp\nbody\n`；paySign `appId\ntimeStamp\nnonceStr\npackage\n`；回调验签 `timestamp\nnonce\nbody\n`。都只差一个字符，但错了就永远签不对，而微信只回 401 |
| **命名差异**                | 请求头是下划线 `timestamp`，小程序参数是驼峰 `timeStamp`。照抄会签出一个永远验不过的 `paySign`，开发者工具只提示「签名失败」                                                           |
| **DTO 刻意不含金额字段**    | 金额一律从商品表读取。前端传「元」而服务端当「分」用是这类接口最经典的事故 —— 不提供这个字段，出错可能性就从「取决于前端写对」变成「结构上不可能」                                     |
| **预支付失败不回滚订单**    | 订单落库是事实，微信侧抖动不该让用户「什么都没发生」。返回 `payment: null` + 原因，前端可稍后重试拉起支付                                                                              |
| 订单号碰撞重试 5 次         | 与邀请码同一策略：碰撞是正常概率事件，抛错会让用户看到「下单失败」，而系统完全有能力自己解决                                                                                           |
| 商品快照含 `snapshotAt`     | 商品价格日后会被运营修改；没有快照时间就无从回答「为什么这个订单是 19.9 而现在是 29.9」                                                                                                |
| 私钥不出 `WechatPayService` | 支付参数由它构造：让调用方拿到私钥再自己签，会把密钥暴露到支付业务代码里                                                                                                               |
