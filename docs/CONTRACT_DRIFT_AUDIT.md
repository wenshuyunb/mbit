# 契约 ↔ 实现漂移审计（2026-10-13）

> 本文是**一次系统盘点的结果**，覆盖 `docs/API_DESIGN.md` §3.2 / §3.3 / §3.4 / §3.6 / §3.7 /
> §3.8 / §3.9 / §3.11 / §3.12 共 9 章 63 个端点（管理端 §3.14 不在范围内）。
> 触发原因：ADR-034 在 §3.5.1 一处就挖出"契约宣称支持、实现必失败"的缺陷，
> 而此前从未系统核对过其它章节。**"文档与实现漂移"是本项目最大的风险来源。**

## 0. 读这份文档前必须知道的判定框架

盘点给出的每一条都要先回答一个问题：**谁才是客户端真正照着写的那一方？**

本项目的实际情况（ADR-033 已立法、本轮再次验证）是：

| 依赖方                                            | 状态                                                       |
| ------------------------------------------------- | ---------------------------------------------------------- |
| 微信小程序 SDK（`frontend/miniapp/src/api/*.ts`） | **既成事实的客户端**，已发布、已联调、逐字使用实现的字段名 |
| 装配后的活体验证脚本（`.runlogs/*.cjs`）          | 按实现写的                                                 |
| Swagger（由实现生成）                             | 等于实现                                                   |
| `docs/API_DESIGN.md`                              | **往往是唯一少数派**                                       |

本轮抽查 5 条"契约说必失败"的高危项，**小程序全部站在实现一边**：

| 项                                  | 契约写法                               | 实现                                                | 小程序                                                                 | 结论                         |
| ----------------------------------- | -------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------- |
| 支付参数外层键                      | `data.payParams`                       | `data.payment`                                      | `uni.requestPayment(order.payment)`（`pkgMember/pages/index.vue:166`） | **契约过期**                 |
| `GET /tests` 响应                   | `{items,total,recommended,serverTime}` | 裸数组                                              | `http.get<TestDefinition[]>('/tests')`（`api/test.ts:190`）            | **契约过期**                 |
| `GET /tests?category`               | `PERSONALITY\|RELATIONSHIP\|ALL`       | `MBTI\|BIG_FIVE\|RELATIONSHIP_STYLE\|COMPREHENSIVE` | `category: string`（`api/test.ts:26`）                                 | **契约过期**                 |
| `GET /tests/sessions` 筛选          | `testCode` / 多值 `status`             | `definitionCode` / 单值 `status`                    | `definitionCode`（`api/test.ts:246`）                                  | **契约过期**                 |
| `POST …/invites/{code}/accept` body | `displayName` / `acceptMessage`        | 空 DTO（**刻意**）                                  | `http.post(..., {})`（`api/relationship.ts:253`）                      | **契约过期**（该能力未交付） |

**因此**：下面标 🔴 的条目绝大多数**不是线上故障**，而是"**照文档新写一个客户端会在第一个请求上失败**"。
它们该按 ADR-033 的判据**改文档**（零运行时风险），而不是改实现（破坏性 + 要让已交付的验证结论失效）。

**真正需要改代码的**，只有两类：
① 实现内部自相矛盾（下节 §1）；
② 被接收却在全链路静默失效的字段（下节 §2）——**这类比 400 更危险**，因为客户端以为生效了。

   「契约 §3.7」（§3.7 是 AI 助手章）；而契约**三处**（§3.9.2 规则 5、§3.9 时序图、
   下单接口说明）都写 `expiredAt = createdAt + 30min`，`/system/config` 的
   `FEATURE_PAYMENT.orderExpireMinutes` 也按 **30** 下发 —— 运营在后台看到 30，实际按 15 关单。
   已对齐为 30，并同步修正 3 处引用（Swagger 描述、`order-query.service.ts` 注释、
   `wechat-pay-sign.util.spec.ts` 里把 15 固定下来的那条断言）。

   > ⚠ **严重度更正**：我最初写成"用户看到 30 分钟、第 20 分钟支付被拒"的投诉级缺陷，
   > **复核后判定说重了** —— 小程序并不消费 `orderExpireMinutes`，用的是下单响应里的真实
   > `expiresAt`（`api/order.ts`），倒计时是准的。真实危害是**配置/文档与实际行为不一致**
   > （会误导运营与后续客户端），而非"用户被坑"。
   >
   > **仍未做的更彻底修法**：让 `orderExpiresAt` 直接读 `payment.orderExpireMinutes`
   > （与 `/system/config` 同源）。否则运营把配置改成 45 分钟后行为仍停在常量上，同类不一致会再次出现。

2. ✅ **已修（2026-10-13）：错误码 `50008` 一码两义（危险内容拦截 vs 对话不存在）**。
   `50008` 是契约 §3.7.5 的**特殊约定**：危险内容命中时 HTTP 200 + `code = 50008`，
   前端据此把关怀文案当**正常消息**渲染（不弹错误 Toast）；而 `AI_CONVERSATION_NOT_FOUND`
   原先也是 `50008` —— 只按 `code` 分支的前端会把"会话不存在"这条 404 渲染成关怀文案，
   用户既看不到真实原因、也拿不到提示。
   复核还发现**契约给"对话不存在"分配的是 `50003`**，而实现里 `50003 = AI_PROVIDER_AUTH_FAILED`
   —— 两边都撞码。最终取空闲的 **`50022`**（`50000`–`50021` 已占用），
   同步更新 `error-code.ts` 的 HTTP 状态表与文案表、重新生成 `docs/ERROR_CODES.md`
   （CI 校验一致性）、契约 §2.4.5 与附录两处表格，并加一条断言防止改回 `50008`。

3. **`GET /relationships/{id}/compatibility` 无报告时返回 `data: null`**，
   而契约明确要求 `200 + hasReport: false`。按文档写 `if (!res.data.hasReport)` 的前端会 `TypeError`。
   `compatibility.service.ts` 里 `if (report === null) return null;` —— 需确认小程序是否已按 `null` 处理。

## 1.5 🔴 全局发现（2026-10-13 新增，**已部分修复**）：查询串布尔值全部被静默取反

**现象**：`?flag=false` 与 `?flag=true` **都会变成 `true`**。

**根因**：`main.ts` 的全局管道开了 `transformOptions: { enableImplicitConversion: true }`，
class-transformer 会**先**按属性的反射类型做隐式转换 —— `boolean` 属性走 `Boolean(value)`，
而查询串里的值**天生是字符串**，`Boolean('false') === true`。
更坑的是 `@Transform` 的回调拿到的 `value` **已经是转换后的布尔值**，因此全仓
**7 份** `toBoolean({ value })` 副本（判 `value === 'false'`）**一次都没生效过**
—— 它们看起来在防这个问题，实际永远走不到字符串分支。

**实测**（临时诊断 spec，跑完已删）：

| 写法                           | `'false'` | `'true'` | `'0'`     |
| ------------------------------ | --------- | -------- | --------- |
| 只有 `@IsBoolean()`            | `true` ✗  | `true` ✓ | `true` ✗  |
| `@Transform(({ value }) => …)` | `true` ✗  | `true` ✓ | `true` ✗  |
| **读 `obj[key]` 原值**         | `false` ✓ | `true` ✓ | `false` ✓ |

**影响**：每一个查询串布尔筛选都在**静默**给出相反结果，例如
`?keepHistory=false`（隐私开关）被当成 `true`、`?hasRefund=false` 只返回**有**退款的订单、
`?includeContent=false` 仍下发正文、`?includeUsage=false` 仍返回用量。
不报错、不写日志 —— 与"绿着但不生效"是同一类，也是最难排查的一类。

**已修**：

1. 新增唯一实现 `backend/src/common/utils/query-boolean.util.ts`
   （从 `obj[key]` 读**原始字符串**，绕开隐式转换；无法识别的值原样透出交给 `@IsBoolean()` 拒绝）。
2. `relationship/dto/relationship.dto.ts`：改用共享实现，并给 `keepHistory`
   **补上 `@Transform`** —— 没有它，上一轮做的隐私开关修复在线上**根本不会生效**。
3. `ai/report/report-engagement.dto.ts`（10 处 usages）：改用共享实现。
4. 新增 `query-boolean.util.spec.ts`：既有直接单测，也有**走与 `main.ts` 同配置的真实
   ValidationPipe** 的用例（这个缺陷恰恰是"函数写对了但接线不对"，只测函数会漏）。

**仍待收敛（下一轮）**：另有 **5 份**同样的 `toBoolean` 副本未改：
`ai/chat/chat.dto.ts`、`payment/refund.dto.ts`、`admin/{user,config,prompt,test-definition}/dto/*.ts`，
以及 `admin/question/dto/admin-question.dto.ts`（它已经收 `{value, obj, key}`，可能部分可用，需逐个验证）。
**判定方法**：跑一次真实管道、传 `'false'` 看是否得到 `false`。

**同类但危害较小的已知项**：**请求体**里的字符串布尔同样被隐式转换
（`{"autoGenerateReport":"false"}` → `true`）。JSON 客户端本来会发真布尔，故危害小得多；
若将来要收紧，给字段加 `@Transform(parseQueryBoolean)` 即可（`'yes'` 会 400）。

### [§3.7.8] ✅ **已修（2026-10-13）**：`nextActions.upgradeUrl`/`creditsUrl` 指向不存在的路由

原值 `/api/v1/membership/plans` 与 `/api/v1/products?type=AI_CREDITS` 在本项目
**一个路由都没有**（ADR-033 已把 `plans`/`products` 合并到 `GET /membership/products`）
—— 而这是「额度耗尽 → 拉起付费墙 → 去升级」的转化路径，客户端照着跳就是 404，
**等于把付费用户挡在门外**，且不报错、不告警。

由 `chat-paywall-links.spec.ts` **与 `MembershipController` 的路由元数据绑定断言**
（直接比别人手写的字面量会在路由改名时依然通过，等于摆设）。
**活体验证**：两个地址实测均返回 `200`（此前 404）。

⚠ 连带发现：`?type=` 这个筛选**在实现里根本不存在**（该端点当时没绑定 `@Query()`），
所以即便链接改对了，用户点"买次数包"仍会看到会员档位混进展厅。
已一并实现 `type` 筛选（`ListProductsQueryDto`），并**活体实测**：
`?type=AI_CREDITS` → 1 件、`?type=MEMBERSHIP` → 3 件、非法值 → `400/10001`。

## 2. 被接收却静默失效的字段（**建议优先修，需改代码或从 DTO 移除**）

**通则**：一个参数被 DTO 收下、却没有任何读取方，比"直接 400"更糟 ——
客户端以为设置生效了（其中还有隐私相关开关），而服务端什么也没做。

| 端点                                     | 字段                                                       | 实际行为                  | 危害                                                                                                                                                                               |
| ---------------------------------------- | ---------------------------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DELETE /relationships/{id}`             | `keepHistory=false`                                        | 完全忽略（表无该列）      | **隐私开关静默失效**：用户以为历史报告已对双方隐藏，实际仍可读                                                                                                                     |
| `POST /relationships/{id}/confirm`       | `autoGenerateReport=false`                                 | 仍按 `true` 触发算分入队  | 用户以为没触发，实际消耗会员额度                                                                                                                                                   |
| `POST /relationships/{id}/compatibility` | `forceRecalculate` / `focus` / `tone` / `includeAdviceFor` | 无读取方                  | "忽略幂等键强制重算"不成立，命中缓存复用旧报告                                                                                                                                     |
| `PATCH /users/me/avatar`                 | `etag` / `width` / `height`                                | ✅ **已修（2026-10-13）** | `etag` 改为按 OSS HEAD **真实比对**（不一致即 `400/10001`）；`width`/`height` 改为**不接收**（无列可存、无策略按尺寸校验，真校验必须解码图片）——传了拿明确的 400，而不是虚假的成功 |
| `GET /system/config?language=en-US`      | `language`                                                 | 静默回退 `zh-CN`          | 语言切换器"选了英文、界面中文、不报错"                                                                                                                                             |

处理建议：**要么实现，要么从 DTO 里删掉**（删掉会让客户端拿到明确的 400，而不是虚假的成功）。

## 4. 已知但未交付的能力（**不是缺陷，是待立项**）

- ✅ **游客可浏览套餐**（契约 §3.8.1 规则 2「转化漏斗需要」）**已实现（2026-10-13）**：
  该端点此前无 `@Public()`，匿名访问返回 `401` —— 尚未登录的新用户看不到任何价格，
  而"先看到价格再决定注册"正是转化漏斗第一步。
  现已标 `@Public()`，匿名返回 `200` + **匿名会员视图**（`isMember: false`、其余 `null`）。
  ⚠ 顺带修掉一个**更危险的连带问题**：守卫原先 `if (isPublic) return true` **直接跳过策略**，
  因此公开接口**即使带合法令牌也不会填 `principal`** —— 若只加 `@Public()`，
  **登录会员会被当成游客**（会员页显示未开通）。
  现改为"**尝试**鉴权、失败按匿名继续"，并给守卫补了 5 条单测。
  活体验证（`.runlogs/probe-guest-products.cjs`）：临时授予真实会员后，
  带令牌 → `isMember: true`、同刻匿名 → `false`、受保护接口匿名仍 `401`。
- 契约声明的 `purchaseNotice`（微信平台合规文案：不会自动续费 + 退款政策）实现里没有。
- `benefitsCompare`（权益对比矩阵，含免费版一行）：本轮已下发 `benefits`（会员档位各自 6 项），
  但"与免费版对比"那层仍未实现。
- §3.9.8 支付回调的失败响应恒为 `200 + {"code":"FAIL"}`（微信侧要求如此），
  契约逐案列了 401/400/409/404 —— 按契约搭的"验签失败立即告警"会**全部漏报**。
  若要该侧信道，应在服务端自行告警，而不是靠 HTTP 状态码。

## 6. 独立抽样复核（2026-10-13，第二轮）—— 修订并不彻底，已返修

### 为什么要有第二轮

第一轮"按实现修订契约"（commit `c700599`）覆盖了 9 章 / 63 个端点，但**只做了抽查**。
为免"改完就当改对了"，本轮派了一个**只读**的独立代理做抽样复核：按 §2.2/§2.9.1/§2.9.2/
§3.2–§3.12 抽 19 条，每条给出「文档行号 ↔ 实现行号」的双向证据，只判 ✅/❌，不改任何文件。

### 结论：19 条里 **9 ✅ / 10 ❌**

漏改的**不是字段表和枚举**（那部分改对了），而是两类"文本块"：

| 漏改类型         | 典型位置                                                                  | 后果                                                 |
| ---------------- | ------------------------------------------------------------------------- | ---------------------------------------------------- |
| **示例代码块**   | §3.2.6 请求/响应、§3.2.7、§3.3.7 响应、§3.8.1 请求+响应、§3.9.1 请求+响应 | 照示例调用直接 `400`，或按旧字段名解析恒 `undefined` |
| **内联错误码表** | §2.2、§2.9.1、§3.2.5 规则、§3.2.6                                         | 为**不存在的码**写分支，真正会收到的码没有分支       |

更危险的是**"加了 ⚠ 更正注就以为改完了"**：§3.2.6、§3.6.3、§3.8.1 三处的 ⚠ 注与它上方
20 行内的原示例/原表**直接互相矛盾**（注说"不能传"，示例偏偏传了）。客户端读哪一段都可能。

**由此定下的新验收条件（已写入返修要求）**：

> **⚠ 注存在 ⇒ 被注对象必须同步改写。** 不允许"注说 A、正文写 B"。

## 7. 下单幂等：从"契约承诺"补成"真实行为"（2026-10-13，已活体验证）

### 问题

契约 §2.9.2 把 `POST /payment/orders` 列为**必须携带 `X-Idempotency-Key`** 的接口，
缺失应返回 `10009`；小程序也确实在发这个头（`frontend/miniapp/src/api/order.ts`）。
但实现的 `createOrder` **既不声明 `@IdempotencyKey()`，也没有任何按幂等键去重** ——
请求头被静默忽略，文档承诺的 `10009` **永远不会出现**，每次调用都新建订单。

危害是资金侧的：客户端相信"服务端会拦住重复提交"因而放心重试，实际每次都产生新订单
（`orders.idempotencyKey` 写的是**服务端随机值**，与客户端键无关）。

### 修法（对齐既有模式，不动 schema）

按 `refund.util.ts` 已验证的「前缀 + sha256 加盐摘要」模式：

- `payment.controller.ts`：`createOrder` 声明 `@IdempotencyKey()`（必填）→ 缺失 `10009`、格式非法 `10001`。
- `payment.service.ts`：**重放短路在任何业务校验之前**（否则商品恰好下架时，重放会拿到 `70001` 而不是首次的成功响应）；
  命中原样返回首次的整份响应（含同一份支付参数）；重放结果整份存 Redis。
- 键空间 `idem:payment:order:{userId}:{sha256(userId:clientKey)[0:32]}`，**TTL = 订单有效期 30 分钟** ——
  订单过期后同键重放应当建新单，否则用户会永久卡在一张付不了款的过期订单上。
- **Redis 故障一律 fail-open**：读失败降级为"未命中"、写失败只记日志。下单是资金主链路，
  缓存不可用不该让用户下不了单；代价（极端情况下多一张未支付订单）远小于"支付整体不可用"。
- 不复用 `orders.idempotency_key` 列：它是 `VarChar(64)` **全局唯一**且当前承载服务端随机值，
  塞客户端键会同时踩到「跨用户撞键」与「超列长度」两个坑。

### 活体证据（`.runlogs/probe-order-idempotency.cjs`，真实 HTTP + Redis + PostgreSQL，9/9 通过）

| 步骤 | 请求                     | 期望                       | 实测                                                     |
| ---- | ------------------------ | -------------------------- | -------------------------------------------------------- |
| A    | 带新键下单               | `201` + `orderNo`          | `201` `SM202610132149044428`                             |
| B    | **同一个键再下一次**     | `201` + **同一 `orderNo`** | `201` `SM202610132149044428`（逐字符相同，支付参数一致） |
| C    | 换一个键下单             | `201` + **不同 `orderNo`** | `201` `SM202610133099502169`                             |
| D    | 不带 `X-Idempotency-Key` | `400` / `10009`            | `400` / `10009`                                          |
| E    | 键格式非法（`short`）    | `400` / `10001`            | `400` / `10001`                                          |
| F    | 订单表净增               | 恰好 `2`（仅 A、C）        | `3 → 5`，净增 `2`                                        |

单测另覆盖：重放不建单/不再请求微信、重放短路在商品校验之前、Redis 读失败降级、
Redis 写失败只记日志、不同用户同键落到不同 Redis 键且客户端键不以明文入键空间；
路由级契约测试**真的把装饰器工厂调起来**，在缺头时断言抛出 `10009`。

### ⚠ 诚实边界：服务端幂等挡不住"每次点击换新键"

小程序 `api/order.ts:97` 在**每次调用时**现取 `createIdempotencyKey()`，而该函数自己的注释写着
"必须在触发操作时生成一次并复用"。因此**双击下单仍会产生两笔订单** —— 这一半只能在客户端修
（复用同一个键 / 请求中禁用按钮）。**服务端这边保证的是"同一操作的重试不会重复建单"**，
不要把它当成双击的完整解法。

## 8. 拿到真实 LLM 密钥后的活体验证发现（2026-10-13）

### 8.1 🔴 已修：`POST /ai/conversations/{id}/messages` 的**双层响应信封**

**这是本轮最有价值的发现，而它此前被 124 个测试套件、tsc、eslint 全部放过。**

实测响应是 `data.data.assistantMessage`。根因：`chat.controller.ts` 的 `sendMessage`
**自己**已经用 `envelope(...)` 构造了完整信封，却**没有标 `@RawResponse()`**，
于是全局 `TransformInterceptor` 又包了一层。

危害远大于"字段错位"：

- 小程序 `request.ts:321` 只解一层信封（`return result.body.data`），拿到的是**内层信封**，
  `assistantMessage` 恒为 `undefined`；
- 更严重的是**危险内容拦截路径**要求**顶层 `code = 50008`**（契约 §3.7.5 明确约定：
  前端按正常消息渲染关怀文案与资源卡、**禁止弹错误 Toast**）。被重新包成顶层 `code = 0`
  之后，前端会当**成功响应**处理 —— 这条安全约定**整体失效**，而它恰恰是自伤高危内容出现时的路径；
- 而该方法内的注释还写着"本方法返回带 `@Res()` 的原始响应"，**代码里根本没有** ——
  注释描述的是从未落地的意图。

**修法**：补 `@RawResponse()`、订正那句与代码不符的注释，并新增 `chat.controller.spec.ts`
做**行为级**守门（不只断言装饰器存在，而是真的把控制器调起来，断言返回值是**单层**信封、
且拦截路径**顶层** `code === 50008`、拦截时不消耗配额）。
**活体复验**：助手回复从 0 字变为 130 字真实中文。

> 教训：这类缺陷的特征是"**单元测试直接构造服务、绕过路由与拦截器**"，因此只有活体 HTTP
> 验证或路由级契约测试才能发现。本项目 §6.3 已记录过同类陷阱，这是又一次同源复发。

## 9. 2026-10-14：报告段落键与契约白名单脱钩（已修）+ 新增测评类型的可行性核查

### 9.1 🔴 已修：报告模板的段落键**不在契约白名单里**

`report-section.util.ts:17-22` 的注释把设计意图写得很清楚：

> 顺序即报告内的自然段序，**取值与生成模板（Prompt 输出 schema）的段落键一致**；
> 让"模板加了新段落、接口忘了登记"变成**编译期问题**而不是线上 400

**这个不变量此前是破的。** 模板产出的是 `overview` / `strengths` / `growth`（3 段、小写下划线），
而白名单 `REPORT_SECTION_KEYS` 是契约 §3.5.4 的 6 个大写键
（`CORE_PORTRAIT` / `DIMENSION_ANALYSIS` / `RELATIONSHIP_PATTERN` / `STRENGTHS_AND_SHADOWS` /
`GROWTH_SUGGESTIONS` / `ACTION_PLAN`）。两者**只是没有被类型连起来**，所以那道安全网从未触发
——更糟的是，`prompt-templates.spec.ts` 里有一条断言把**错误约定固化**了：
它要求段落键必须匹配 `/^[a-z][a-z0-9_]*$/`（小写），于是谁改都不会有人质疑。

可复现的后果有两个：

1. **`quoteSectionKey` 永远取不到段落** —— 该字段由 `@IsIn(REPORT_SECTION_KEYS)` 校验
   （`report-engagement.dto.ts:242`），客户端**只能**传那 6 个大写键；而
   `report-share-card.service.ts:348` 按该键去 `report_sections.section_key` 里找 ——
   真实报告存的是 `overview` 等。**分享卡的「金句卡」（QUOTE_CARD）在真实报告上必然返回
   `10001 指向的段落不存在`，从上线起就没可能成功过**；
2. **报告只有 3 段、实测 864 字**（契约 §3.5.3 给的是 6 段、`targetSectionCount: 6`、
   目标篇幅约 3300 字），用户直接反馈"过于简陋、没有建设意见"。

**修法**：把 `report.mbti` 的段落声明改成契约的 6 段（键名与标题逐字对齐）、
每段字数上限从 150–300 放宽到 350–600、`maxTokens` 2048→4096、模板升到 **v2**（保留 v1 供历史报告对号）。

| ----------------------- | ---- |
| `CORE_PORTRAIT`         | 419  |
| `DIMENSION_ANALYSIS`    | 456  |

| `STRENGTHS_AND_SHADOWS` | 384  |
| `GROWTH_SUGGESTIONS`    | 406  |

- `TEMPLATE_KEY_BY_TYPE` + 新的上下文组装器 + 模板 + spec 路由。

这是本次改动**唯一**的行为差异，不要漏记：

- **改之前**：用户提交测评时算一次，把依恋 / 爱的语言 / 冲突处理**写进画像列**。
  此后运营改 `relationship_style_rules`，**历史用户的值不变**。
- **改之后**：每次读取时按当前规则表现算。运营改规则表，**历史用户的推导值同步改变**。

**为什么接受**：规则表是**产品配置**而不是用户数据。原先那种"配置改了却对老用户永远不生效"
的状态更难解释（同一个大五分数，新老用户拿到不同的依恋风格），而且会让配置调优失去意义。
**为什么现在必须写明**：情感模块（阶段 3）会用**自己的题目直接测量**依恋与爱的语言，
那才是真实观测值；届时"推导值"只是**没做过情感测评时的兜底**，文案上不得把它说成"测出来的"。

### 10.3 证据：等价性是被验证过的，不是被声称的

`.runlogs/probe-derive-parity.cjs`（真实 PostgreSQL + 真实画像 + 真实权重矩阵）：

- **逐画像比对**：库中 2 份画像的 `attachmentStyle` / `loveLanguages` / `conflictStyle`
  与推导结果**逐字段相等**；
- **分数对照**：库里**没有**任何匹配报告（因此这一段原本会**空跑**，等于没验），
  探针因此改用现有画像**合成对照对**，用「库列」与「推导」各算一次：
  `total=87.4 / 依恋=95 / 沟通=100`（自比）与 `total=86.6`（两份真实画像互比），
  五条分数（总分 + 四个子项）**两条路径完全一致**。

配套 `relationship-style-derivation.spec.ts` 把这条不变量钉成常驻测试：
以 `PersonalityEngine.compute()` 为**唯一权威对照物**，断言
`derive(compute().bigFive, 规则)` 与 `compute().relationshipStyle` **逐字段相等（含 `matchedRuleCode`）**，
覆盖命中 / 无规则 / 全部不命中 / 优先级竞争 / 同优先级按 code 排序 / 维度缺作答（`null → 50` 兜底）。

### 10.4 顺带修掉的一处真实隐患：规则数组的别名共享

`resolveRelationshipStyle` 此前有两处**返回共享引用**：

1. 命中规则时 `loveLanguage: rule.resultLoveLanguages`（直接引用规则对象的数组）；
2. 未命中时 `{ ...DEFAULT_RELATIONSHIP_STYLE }` —— 对象展开**只复制属性**，
   `loveLanguage` 仍是那个**模块级空数组**的同一个引用。

后果是任何消费方对结果数组做一次 `push`，就会改脏规则表本身或"此后进程内所有默认风格"，
表现为"后来某个用户的爱的语言莫名多了一项"，且不报错。现已改为返回**新建数组**，
并用测试固定（`relationship-style-derivation.spec.ts` 的两条别名断言）。

### 10.5 🔴 活体验证暴露的新缺陷：人格报告**编造**了依恋风格（已修，v4 模板）

**发现方式**：`.runlogs/probe-ai-live.cjs` 生成的真实报告里，`RELATIONSHIP_PATTERN`
（「你的关系模式」，**付费段**）写着：

> 「结合**安全型依恋**与**协作式冲突风格**来看，你整体……」

而阶段 2 第一步（commit `f38cb5e`）已经把 `{{attachmentStyle}}` / `{{loveLanguages}}` /
`{{conflictStyle}}` 从 `report.mbti` / `report.bigfive` 模板里摘掉了 ——
**提示词里没有任何依恋数据**，这句是模型看到标题「你的关系模式」后自己编的。

**为什么这条比"少给数据"更严重**：编出来的结论落在**付费段**，用户会把它读成"测出来的结果"。
"摘掉变量"只保证模型**拿不到**数据，不保证它**不说**。

**修法**：给段落声明加可选的 `hint`（写作要求），由 `buildSectionFormatInstruction`
渲染进提示词，并给 `RELATIONSHIP_PATTERN` 写死边界：只从 MBTI / 大五谈关系表现，
**严禁**给出依恋类型 / 爱的语言 / 冲突风格。模板版本 v3 → **v4**，`changeNote` 记录原因。

**为什么做成通用机制而不是只改这一段**：其余模板迟早会遇到同类问题
（"标题诱使模型输出本模块没有的数据"），有一个 `hint` 位比每次去改提示词正文更好维护。
刻意做成**可选**：硬给每段都编一条要求会让提示词变吵、稀释重点。

配套测试（`prompt-templates.spec.ts`）：人格报告模板**不得包含**那三个情感变量、
`RELATIONSHIP_PATTERN` 必须有 `hint` 且必须"真的渲染进提示词"
（否则 hint 只是种子数据里的一句注释）。

**修复后的活体验证**（`.runlogs/probe-emotion-leak.cjs`，真实 DeepSeek + 重新灌种子后的 v4）：

- 生效版本确认为 **v4**，`RELATIONSHIP_PATTERN.hint` 已落到 `outputSchema.sections`；
- 重新生成一份真实报告（`reportId=01a1388b-…`）：**6 段全部**不含
  依恋 / 爱的语言 / 冲突风格措辞（机械扫描 9 个禁用词，0 命中）；
- 该段改为**完全从 MBTI 四维展开** —— 逐段谈内向倾向的独处需求、直觉倾向的整体性问题、
  情感倾向的优先他人感受、知觉倾向对不确定性的容忍，末句是
  「你的挑战或许不在于『爱不爱』，而在于如何让对方看见你内心的那些细腻活动」。
  这正是人格模块**该**产出的内容：把人格特质如何在关系里表现讲清楚，
  而不是给出一个本模块没有测过的情感类型。

⚠ 该探针的机械扫描只是辅助：模型换一种说法表达相近意思是合理的，
**不得**把"没出现禁用词"当成"一定没有越界"。最终仍需人工读一遍正文。

### 10.6 这一步**没有**做的事（诚实边界）

- **四列还没删**：本步只把读者搬走，写入方（`test.service.ts` 画像创建）与
  只读暴露（`GET /personality/me`、`GET /users/me?include=profile`、管理端用户详情）
  仍在读写这四列 —— 删除是**下一步**（见 §11），顺序不能反（先删列会让上面四处直接编译失败）。

  `POST /relationships/{id}/compatibility` 无法真实调用。因此"匹配报告能生成"这一点
  目前只有**合成对照**（10.3）与单元测试支撑，**没有**真实的"发起匹配 → 轮询 → 拿到报告"证据。
  演示用户与真实微信用户之间**没有**建立关系，是刻意不做的 ——
  在用户手机上凭空多出一个"伴侣"比留一个未验证项更糟。

**之后没有启回来**。而 `POST /reports` 是**幂等**的：同一份画像 + 同一 Prompt 版本

探针验证的是"这份报告存在"，而它本该验证的是"这次请求能被生成"。

1. **前置检查**：先查该用户是否已有该类型的成功报告，有就直接**失败退出**

2. **显式断言 `isReused !== true`** —— 复用即失败；
3. 请求一个**此前从未生成过**的类型（`BIG_FIVE_REPORT`），断言终态 `SUCCEEDED`

实测 **5/5 通过**：`isReused=false`、`GENERATING → SUCCEEDED`、
4 段落库（341 / 318 / 296 / 324 字）、1720 tokens。

> **教训（写下来避免重犯）**：任何"异步 + 幂等"的链路，
> 只断言"最终有个成功结果"是**不足以**证明链路可用的 ——
> 必须断言"**这一次**确实做了工作"。凡是带 `isReused` / `cacheHit` / `skipped`
> 这类标志的接口，探针都要显式检查它，否则就会出现"后端全绿、用户点下去没反应"。

## 12. 2026-10-14（续）：ADR-038 阶段 3 —— 情感模块落地

### 12.1 这一步补的是什么

阶段 1–2 把情感结论从人格域**清干净**了（删了 7 列 / 3 张表），但情感模块
**本身还不存在**：用户做不了情感测评，界面上也没有入口。阶段 3 把它建起来。

### 12.2 引擎用的是三个**公认模型**，不是自编维度

| 族       | 模型                        | 计分轴         | 结论怎么来                           |
| -------- | --------------------------- | -------------- | ------------------------------------ |
| 依恋     | ECR（亲密关系体验量表）双轴 | 焦虑轴、回避轴 | 两轴**求交** → 四象限 → 四种依恋类型 |
| 爱的语言 | Gary Chapman 五种爱的语言   | 五项各自得分   | 按分数排序取前两名                   |
| 冲突风格 | Thomas–Kilmann（TKI）五种   | 五项各自得分   | 取最高分者为主导风格                 |

用户对情感分析的要求是「**专业、简单易懂**」：专业落在"用公认模型、结论可追溯到
具体分数"，简单易懂落在"报告里不说量表术语"。两者都不靠玄学。

**为什么依恋必须落库两条轴而不只存类型标签**：四种类型是两条连续轴的**象限划分**，
标签丢掉了"离分界线多远"。只存标签，报告就只能写"你是焦虑型依恋"——
而用户对产品的原话是「不要过于简陋」。

### 12.3 抽出了共用的算分数学（`common/engine/assessment-scoring.util.ts`）

单题有效值、量表解析、维度累加与归一化，从人格引擎抽出来由两个引擎共用。

**抽的理由不是"代码整洁"**，而是这些边界语义必须两处完全一致：
反向计分是 `scaleMin + scaleMax − value`（量程不一定从 0 起）、`resolveScale` 的
三级优先级、排序题位置分在单选题上的退化处理。各写一份的话，
同一份作答会被人格与情感两个模块以不同口径评分，**而且不会有任何报错**。

质量指标（一致性 / 完成率 / 平均耗时）同理：`computeConsistency` 必须比较
**反向修正之后**的值，混用会让"一条线全选满分"被判成高一致性 ——
那个 bug 真实发生过。抄一份到情感引擎，这条教训就要在两处分别保持正确。

顺带把 `engine-math.util.ts` 迁到 `common/engine/`：它原先住在 `personality/engine/` 下，
导致 `common/engine/assessment-quality.util.ts` 必须**反向依赖** `modules/personality` ——
而 `common` 本该是依赖图的叶子。

### 12.4 `ModuleScoringService` 搬出了人格模块

它现在要同时引用人格引擎与情感引擎。留在 `personality/engine/` 下就等于
`personality → emotion`，与"三个模块互不干扰"直接冲突（哪怕只是 import）。
移到唯一的消费方 `test`（测评管道）后，依赖方向是
`test → personality` + `test → emotion`，两条都单向。

同时把返回值从 `PersonalityEngineOutput` 扩成**按模块判别的联合类型**
（阶段 1 的注释就写了"等有第二个实现再扩，那时有真实实现驱动形状"—— 现在正是）。

### 12.5 提交落库：情感走自己的分支

| 差异点         | 人格模块                                         | 情感模块                                                   |
| -------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| 完整性门禁     | 以 MBTI 四字母为骨架，算不出类型就不写画像       | 三个族**各自**判定，缺哪个族报哪个族（`40016`）            |
| `test_results` | 写 MBTI / 大五列                                 | 这些列**留空**（借用会被日后的统计与成长曲线当人格分数读） |
| 画像表         | `personality_profiles` + `personality_snapshots` | `emotion_profiles`（**没有**快照表）                       |
| 错误码         | `40010/40011/40012`                              | `40014/40015/40016`（**平行而不复用**）                    |

⚠ 情感分支必须放在人格那道门禁**之前**：`mbti.type === null` 是人格专属判据，
情感结果走进去必然被判"算分失败"，并把用户已答的数据置为 `EXPIRED`。

错误码故意不复用：复用会让前端分不清是哪个模块没画像，
而两者的引导文案完全不同（一个引导做人格测试，一个引导做情感测评）。

`SubmitResultView` 改成按 `module` 判别的联合类型 ——
"一个包含全部可选字段的大对象"会让人格接口莫名其妙地暴露情感字段，
正是阶段 2 刚清掉的那类问题。

### 12.6 题库规格的自相矛盾（**发现并修正，值得记下来**）

按 42 题（爱的语言/冲突风格每项 3 题 = 2 正 + 1 反）设计后，
`seed-data.spec.ts` 的「前后半区都要有反向题」守卫**无法通过**：

```
题量 3 → half = 1 → 前半区是 flags[0]，后半区是 flags[1..2]
1 道反向题在数学上不可能同时落进这两个互斥的集合
```

这条守卫此前只服务过 8 题 / 10 题的维度，**从未被短维度触发过**，
所以问题一直没暴露。

**修法是补题量而不是放宽守卫**：每项从 3 题扩到 4 题（2 正 + 2 反），
全卷 52 题。理由：为迁就数据去放宽一条已有守卫通常是错的；
而且每项只有 1 道反向题时，该维度的一致性评分本身也偏脆
（拿 2 个正向值的均值与 1 个反向值比较）。4 题两头都解决了。

## 13. 2026-10-14（续）：ADR-038 阶段 5 —— AI 助手改为「读三模块的会员管家」

### 13.1 这一步补的是什么

用户的原话是「AI 助手也重新设计，做成是可以读取三个模块的报告的那种，
类似小程序管家的角色，用户可以让他总结，并且等等之类的功能，但是，需要加入会员才可以使用」。

三个关键词各自对应一处实现，缺任何一个这个角色都不成立：

| 关键词           | 实现                                                             | 落在哪                                                       |
| ---------------- | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| **三个模块**     | `contextHints: ['ALL_MODULES']` → 三个模块画像摘要               | `chat-context.service.ts` / `chat.types.ts`                  |
| **管家（总结）** | 提示词与前端文案从"情感助手"改为"管家"，快捷提问首位是"帮我总结" | `chat-prompt` 模板、`pkgChat/pages/index.vue`                |
| **会员才可用**   | 配置项 `ai.assistantMembersOnly`，两条写入路径强制               | `chat-quota.service.ts`、两个写入服务、`system-configs` 种子 |

### 13.2 门槛做成配置项，且**读不到时按"拦"处理**（fail-closed）

`ai.assistantMembersOnly` 是系统配置（BOOLEAN，默认 `'true'`），不是常量。
理由：它决定**免费用户能否使用助手**，属于运营策略；试运行期想放开、想回滚，
都只改一个值而不该发版。

读取时有一个刻意的方向选择：

```ts
// chat-quota.service.ts
const FALLBACK_ASSISTANT_MEMBERS_ONLY = true;
```

配置行缺失、值非法（例如 `'yes'`）或类型读不出来时，一律按 **`true`（拦）** 处理。
反方向（默认放行）的故障形态是"配置表被清空/迁移中途时，全站免费用户都能白嫖 AI"，
这比"短暂地谁都用不了"严重得多 —— 且后者会立刻被用户发现，前者只会在月底账单上发现。

同时**必须用 `readBoolean()` 而不是 `Boolean(value)`**：`Boolean('false') === true`，
这个陷阱在本仓已经踩过（见 §1.5），所以 `chat-quota.service.spec.ts` 专门断言了
字符串 `'false'`、未知值回落、配置缺失三种输入。

### 13.3 拦在**两条**写入路径上，`/ai/quota` 只报告不抛错

| 位置                                   | 行为                                                          |
| -------------------------------------- | ------------------------------------------------------------- |
| `POST /ai/conversations`               | `assertAssistantAccess()` 在 `claimIdempotency` **之前**      |
| `POST /ai/conversations/{id}/messages` | 调用配额预占**之前**先过一次门槛                              |
| `GET /ai/quota`                        | **不抛错**，回 `assistantMembersOnly` + `nextActions.canChat` |

- **只拦一处不够**：只拦建会话，用户拿一个历史会话就能继续发；
  只拦发消息，会在库里留下一堆建好但永远发不出消息的空会话。
- **顺序**：门槛检查放在幂等占位之前。反过来的话，被拦的请求会先占掉一个幂等键，
  用户开通会员后**用同一个 key 重试**会直接拿到上次的拒绝结果 —— 一个已经付费的用户
  被自己的重试卡住，且错误信息与门槛毫无关系。
- **错误码不复用配额码**：`70016 ENTITLEMENT_REQUIRED`（403），不是 `50006`。
  两者出路完全不同（开会员 vs 买次数包/等明天），前端要据此走两条不同的引导，
  合并成一个码等于把"要不要花钱、花在哪"这个决策交给文案去猜。
- **`/ai/quota` 不抛错**：前端恰恰要靠这个接口告诉用户"你需要开通会员"。
  在这里抛 403 会让"查看剩余额度"变成一次失败请求，前端只能靠试错来发现门槛。

### 13.4 `ALL_MODULES` 读的是**画像**，不是报告

用户说的是"读取三个模块的**报告**"，但**字面实现第三个模块必然是空的**：
心理状态模块刻意不做 AI 报告（§12 阶段 4 的红线 —— AI 解读几乎必然滑向建议）。

因此摘要读三张**画像表**：

```
personality_profiles  /  emotion_profiles  /  mental_health_profiles
```

三个模块都有画像，报告则不一定（免费用户可能没解锁、生成可能失败）。
规格：**没测过的模块直接省略**，不写"未测评" ——
后者会在提示词里制造一个不存在的观测，模型很可能据此编出"你尚未测评"之外的结论。
单块长度上限 `HINT_TEXT_LIMIT * 2`，越界整块丢弃而不是截半句。

这条差异已同步到 `API_DESIGN.md` 的 `contextHints` 说明（ADR-033 判据：
实现 + 客户端都需要，改契约文档）。

### 13.5 探针发现的两个实现缺陷（**都不是类型问题**）

活体探针 `probe-butler-gate.cjs` 第一版 14/20，暴露两处：

1. **`contextHints` 传错了接口**：第一版把它传给 `POST /ai/conversations`
   （`CreateConversationDto` 没有该字段），全局管道 `forbidNonWhitelisted`
   直接回 `400 / 10001 property contextHints should not exist`。
   语义上它本来就该在**发消息**上："这一轮额外注入什么"是单次请求的属性，
   不是会话的固有属性。DTO 是对的，探针写错了；
2. **改库不等于改配置**：E 段直接把 `value` 写成 `'false'`，但
   `SystemConfigService` 的快照缓存在 Redis（`sm:system:config`，TTL 300s），
   改库不失效缓存，接口读到的还是旧值 —— E1/E2 因此全挂。

第 2 点值得单独记：它说明**"绕过后台直接改库"不是一条真实运维路径**。
真实路径是后台面板（`PUT /admin/configs`），它写库后会主动 `invalidate`。
探针改成走后台接口后，顺带把「写配置会主动失效前台缓存」这一环也验证了 ——
这一环断掉的表现是「后台显示已关闭、用户端最长 300s 仍被挡」，
属于**只在生产上偶发、无法复现**的那类故障。

改完后：**24/24 通过**（A 拦截 4 项 / B 放行 2 项 / C 三个测评 / D 回复 5+4 项 / E 配置 6 项）。

D 段的回复（真实 DeepSeek，199 字）同时提到三个模块：

> 人格这块，你是 ESFJ 型……亲密关系上，你是安全型依恋，焦虑和回避都不算高，
> 爱的语言偏向接受礼物和精心的时刻，冲突时更倾向主动争取、把话说开。
> 近两周的状态整体有些起伏，情绪低落和缺少支持这两块相对明显，睡眠倒还算平稳。

且不含「诊断 / 抑郁症 / 焦虑症 / 用药」四个词 —— 管家在复述心理状态模块时
同样守住了"不给建议、不做诊断"的边界。

### 13.5.1 ⚠ D 段差点变成"测模型措辞"：关键词断言的两个方向都会错

第二轮复跑时 `D4`（回复提到情感模块）**误报失败**。原因不是实现退步，
而是模型换了一种**全转述**的措辞：

| 复跑   | 模型原话                                                     | 关键词断言           |
| ------ | ------------------------------------------------------------ | -------------------- |
| 第一次 | 「你是**安全型依恋**，**爱的语言**偏向接受礼物和精心的时刻」 | 命中（有标签）       |
| 第二次 | 「你比较需要自己的**空间**，但也挺在乎被认真对待的时刻」     | **未命中**（无标签） |

第二次的画像实际是「回避型依恋 + 精心的时刻」—— 模型读到了，只是没照抄标签。

修法有两条路，**只有一条是对的**：

- ❌ 把关键词放宽到「空间 / 陪伴 / 关系」这类通用词 —— 会引入反向错误：
  模型**自己编出**情感内容时也会命中，而这正是阶段 2a 修过的真实缺陷
  （人格报告模板凭空写出"安全型依恋"）。断言太宽 = 把一次真实回归放行；
- ✅ **期望值从库里读**：先查该用户真实的三份画像，再从画像推出"只要真读了就总要提到"的词
  （他自己的依恋标签 / 爱的语言 / 高亮维度，以及各自的常见转述），
  命中必须落到**他自己的结果**上。再配合把提问改成明确点名三个方面
  （管家本来就该三块都说清），标签复述率也随之稳定。

修完复跑：`D4` 命中 `["恐惧型","接受礼物","礼物","精心的时刻","一起"]`，
`D5` 命中 `["压力","紧张不安","紧张","不安","焦虑"]`，且与库里的
`FEARFUL` / `LOVE_GIFTS`+`LOVE_TIME` / `MH_STRESS`+`MH_ANXIETY` **逐项对得上**。

### 13.5.2 但"读到三个模块"这件事**不能**只靠问模型 —— 补一个确定性探针

D 段无论怎么改，本质都是"看模型说了什么"，它证明不了"摘要里真的有三个模块"：
模型可能只读到一个模块，然后用通用的心理/关系话术把三个方面的提问都答了。

因此新增 `probe-module-digest.cjs`：**同进程**起一个 Nest 应用上下文（不开端口，
不与 3000 冲突），直接读摘要字符串本身。**11/11 通过**：

```
A. 只做了人格测评时：摘要只有【人格】一段，🚫 不含情感段、不含近两周状态段
   （"没测过就不能凭空出现"—— 这条正是防"模型编造模块"的那一半）
B. 三个模块都测过后：三段齐全，且
   · 人格段带的是库里那个 MBTI 类型（INTP）
   · 情感段带的是库里依恋编码对应的中文标签（AVOIDANT → 回避型）
   · 近两周段注入的是**服务端已给出的结论原文**（不是让模型重新解读一遍）
C. 三个模块都没测时返回 null（不产出空摘要、不写「未测评」）
```

分工因此明确：**摘要有三个模块** = 确定性探针；**助手会用三个模块** = 端到端烟雾。

> 这条经验可以推广：凡是"AI 有没有按我们给的数据说话"的验证，
> 断言都不要落在模型的**措辞**上。要么断言输入（确定性），
> 要么断言输出里**只有该输入才能产生**的具体值。

### 13.6 前端：付费墙与"次数用完"必须分开

小程序端新增 `src/pkgChat/chat-gate.ts`（纯函数），把三种状态分开：

| 场景                   | `assistantMembersOnly` | `canChat` | 展示     |
| ---------------------- | ---------------------- | --------- | -------- |
| 免费用户，门槛开着     | `true`                 | `false`   | 开通会员 |
| 门槛已关，免费额度用完 | `false`                | `false`   | 买次数包 |
| 会员，额度充足         | 任意                   | `true`    | 正常输入 |

两个刻意的选择：

- **抽成纯函数而不是写在 SFC 的 `computed` 里**：判定逻辑在组件内没法单测，
  而"该展示会员引导还是次数用完"正是本阶段最容易写错的一处（20 例单测锁死）；
- **配额未加载完（`null`）时一律不拦**：宁可先让输入框可用（服务端仍会兜底拦），
  也不要让老会员每次进页面都闪一下付费墙 —— 那是最容易被投诉的假故障。

同一轮里 `src/api/chat.ts` 还修掉两个"看起来能跑"的缺陷（见 §13.7）。
`tests/api/chat.spec.ts` 与 `tests/pkg-chat/chat-gate.spec.ts` 共 +20 例。

### 13.7 顺带修掉的两个真实缺陷

1. **小程序端的聊天类型与后端完全对不上**：
   `ChatMessage` 写成 `{ id, meta: { model, latencyMs } }`，
   实际是 `{ messageId, model, latencyMs, ... }`（无 `meta` 子对象）；
   `Conversation` 缺 `conversationId`、多了不存在的字段。
   因为聊天页一直是「Phase 5 接入」的占位实现（`send()` 里只有一句 toast），
   `tsc` 看不见、也没有任何测试覆盖 —— **契约漂移的典型形态**；
2. **发消息与建会话缺幂等键 → 点一次必然 400**：
   两个接口的 `@IdempotencyKey()` 默认必填，而请求层只在**显式传入**时

### 13.10 🔴 顺带发现的**付费墙错误码整段错位**（本阶段只修了被触及的 5 行）

改 `API_DESIGN.md` 时对着 `error-code.ts` 逐值核对，发现 §2.4.7 的
`70014`–`70018` **码值、语义、HTTP 状态三者全部错位**：

| 码值    | 契约原文（错）            | `error-code.ts` 实际（对）                       | 危险在哪                                                   |
| ------- | ------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| `70014` | 402「该功能需要会员权益」 | `MEMBERSHIP_NOT_FOUND` 404「会员信息不存在」     | 客户端会把"没有会员记录"当成"要买会员"弹付费墙（碰巧同向） |
| `70015` | 404「权益不存在或已过期」 | `MEMBERSHIP_EXPIRED` 403「会员已过期」           | 404 会让前端去"刷新权益列表"，而实际该做的是续费           |
| `70016` | 402「AI 对话次数已用尽」  | `ENTITLEMENT_REQUIRED` 403「该内容需要付费解锁」 | **最严重**：把"开通会员"引导成"再买一次次数包"             |
| `70017` | 502「微信查单失败」       | `ENTITLEMENT_NOT_FOUND` 404「权益不存在」        | 完全无关的两件事共用一个码                                 |
| `70018` | 503「支付通道未配置」     | `PAYMENT_FEATURE_DISABLED` 403                   | 语义接近，但状态码不同（503 会让客户端当成"稍后重试"）     |

外加一条全局事实：**`error-code.ts` 里没有任何一个错误码映射到 HTTP 402**。
契约 §2.4.3 的 402 行、以及各接口小节里的 `402`（`50001`/`50015`/`70014`/`70016`）全是过期值；
实现里付费墙类错误一律 `403`，配额不足是 `50006 AI_QUOTA_EXCEEDED`（403）。

本轮**只改了被阶段 5 直接触及的部分**：§2.4.7 的 70014–70018、附录 C.7 对应行、
§2.4.3 的 402 行、以及 §3.7.1/§3.7.5/§3.7.6 新增的 `70016` 行 ——
因为新加的门槛抛的就是 `70016`，留着"70016 = 次数用完"的总表等于让下一个人照着错的写。
**其余小节（§2.4.5 段 50 与附录 C.5 等）没有一起动**：它们的错位与本次改动无关，
且那些小节大多已带「以 `error-code.ts` 为准」的 ⚠ 注记。
整段收敛应作为独立一轮，逐码比对 `error-code.ts`（**唯一事实源**），
不要在一次功能交付里顺手重写一张几千行的错误码表。

> 这一条值得记下来的原因不是"文档过时"，而是**错位方向恰好指向付费转化**：
> 付费墙的每一个码都在决定用户下一步花不花钱、花在哪。
> 码值错位不会让任何测试变红（没有测试断言文档），只会让真人多点一次、
> 或者干脆放弃 —— 属于"指标掉了但查不出原因"的那类问题。

## 14. 2026-10-15：第一次真机实测——答题页**静默漏答**（已修）

### 14.1 用户报的现象与日志里的真相

用户在微信开发者工具里做 52 题的情感测评，报：「做到 48 题就不给下一题了，
点提交也提交不了」。服务端日志与库里的数据把这件事讲清楚了：

```
10:10:06  创建会话 EMOTION_LITE questions=52
10:10:06  GET /tests/sessions/…?batch=1 / =2 / =3      ← 三批都取到了，前端手里是完整 52 题
10:10:34  POST …/submit → 400 / 40006
          message: 还有 4 道题未作答
          details: 未作答的题号：10, 34, 37, 49
```

**缺的 4 题是散落的**（第 10、34、37、49 题），不是末尾 4 题。
这个形状就是判据：

| 缺口形状 | 含义                   |
| -------- | ---------------------- |
| 末尾连续 | 用户没做完就提交       |
| **散落** | 答题过程中**被跳过去** |

库里的答案是 48 条、且 `PUT /answers` 一路都是 200 ——
说明这 4 题**从来没进过前端的答案表**，不是"同步丢了"。

### 14.2 根因：自动跳题的定时器取消不掉

```ts
// 修改前（pkgTest/pages/quiz.vue）
if (!isLast.value) setTimeout(() => testStore.next(), 180); // 句柄没保存
```

```
t+0      点选项 → 排一个 180ms 后 next()
t+50     用户觉得"怎么没跳"，顺手点了「下一题」 → next()   → 第 n+1 题
t+180    定时器到点 → next()                              → 第 n+2 题
         第 n+1 题**从未显示**，也就永远不会有答案
```

而界面上**没有任何地方能发现这件事**：题号面板只在用户主动点开时出现，
底部的「48 / 52」也只说明"还差 4 题"，不说是哪 4 题 ——
在 52 题里找一个漏掉的题，靠人眼是不可能完成的任务。

### 14.3 修法分两层（只修一层都不够）

1. **消除竞态**：自动跳题抽成 `src/pkgTest/auto-advance.ts`，
   句柄可取消；所有手动翻页路径（上一题 / 下一题 / 题号跳转 / 补答）与页面卸载
   都先 `cancel()`；重复 `schedule()` 只保留最后一次。
   抽成独立模块是为了**能用假定时器精确验证** —— 时序逻辑留在 `.vue` 里只能靠肉眼看；
2. **让漏答可见、可操作**（`store/test.ts` 新增 `firstUnansweredIndex` / `unansweredCount`）：
   - 底部常驻「还有 N 题未作答 · 去补答」，点一下跳到**第一道**缺题；
   - 提交时若未答完：只给「去补答」一个出路；
   - **续答落点也按缺口走**：草稿里有漏答时直接回到第一道缺题
     （没有缺口才保持用户上次停留的位置，不打断正常的回头检查）——
     这条专门为了让**已经被卡住的用户**重新进入时不用自己找缺口。

> ⚠ 第二条不是锦上添花。竞态修掉之后，"漏答"仍可能因为别的原因出现
> （网络重放、跨设备续答、用户主动跳过）。**只要漏答还能发生，
> 就必须有一个把它变成可操作状态的地方**，否则用户永远卡在"提交不了"上。

### 14.4 顺带修掉的三个缺陷

1. **未答完时的确认框是个死路**：原实现给的是
   `confirmText: '继续作答'` + `cancelText: '仍要提交'`，而**服务端规则是
   "题量不完整即拒绝算分"** —— 点"仍要提交"必然 400。一个只会失败的主意
   不该出现在选项里，现在只剩「去补答」；
2. **服务端 400 被静默吞掉**：`submit()` 的 catch 只 `console.error`，
   用户看到的是"点了没反应"。现在会把用户送到第一道缺题处；
3. **`clearDraft()` 的题库白名单漏了两个新模块**：原先写死
   `MBTI_FULL / MBTI_LITE / BIG_FIVE_50`，阶段 3/4 新增的
   `EMOTION_LITE` / `MENTAL_HEALTH_LITE` 不在其中 ——
   做完情感测评后草稿**永不清除**，下次进入"情感测评"会复活一个**已提交过**的会话
   （题目、作答、进度全是旧的）。现在按当前试卷的 `testCode` 清，不再维护白名单。
   同一个 bug 的另一面：`abandon()` 先把 `paper` 置空再调 `clearDraft()`，
   于是连旧白名单那几个也删不掉 —— 已改为先删草稿再清内存。

## 15. 2026-10-15：ADR-039 第一步 —— 性别基座（`genderDeclared`）

### 15.1 这一步补的是什么

用户要求情感测评改成**沉浸式场景题**，并按性别出题与出报告（完整决策见
`PROJECT_ARCHITECTURE.md` ADR-039）。开工前先把**性别这件事本身**做扎实，
因为它决定后面每一步出哪套题：

| 事实           | 现状                                                          | 这一步做了什么                  |
| -------------- | ------------------------------------------------------------- | ------------------------------- |
| `users.gender` | 早就有列（`UNKNOWN`/`MALE`/`FEMALE`/`OTHER`，默认 `UNKNOWN`） | 不动                            |
| 前端性别入口   | **一个都没有**（`gender` 只出现在类型定义里）                 | 首启引导 + 个人中心可改         |
| 「问过没有」   | **无法表达**                                                  | 新增 `users.gender_declared_at` |

### 15.2 为什么必须多一个字段（而不是复用 `UNKNOWN`）

`UNKNOWN` 有两种来源，产品含义完全不同：

| 来源                   | 取题结果   | 交互                 |
| ---------------------- | ---------- | -------------------- |
| ① 从来没问过           | 中性版场景 | **要弹引导**         |
| ② 问过了，用户选择不说 | 中性版场景 | **不能再弹**（骚扰） |

只看 `gender` 无法区分；只在前端记标记也不行 —— 换设备/清缓存后回到①。
因此把"**被询问过**"当成一个独立事实落库：**用户做出选择时置位（包括选「不想说」）**，
改性别不重置。语义是"问过了"，不是"填了"。

### 15.3 两个方向的失败都是静默的（所以两面都写了断言）

| 失败方向               | 表现                                   | 谁来兜                              |
| ---------------------- | -------------------------------------- | ----------------------------------- |
| 该弹不弹               | 用户永远拿中性版场景，界面上看不出异常 | 服务端判定 + 探针 A3                |
| 不该弹却弹             | 选了"不想说"的人每次冷启动被再问一遍   | `genderDeclared` 独立字段 + 探针 C3 |
| 字段缺失时误判为"问过" | 同"该弹不弹"                           | 前端只在**严格 `false`** 时才弹     |

最后一行是个刻意的方向选择：`undefined`（还没拉到 `/users/me`）**不算"问过"**，
但前端也**不因此弹窗** —— 兼顾"不把缺失当问过"与"冷启动不闪弹窗"，
靠的是 `needsGenderSetup = isLoggedIn && genderDeclared === false`（严格等于 `false`）。

## 16. 2026-10-15：ADR-039 第二步 —— 把场景题的算分链路接通

### 16.1 这一步的核心：一条**四个环节都断了**的链路

场景题与量表题的根本差别在"分值挂在哪"：量表题的分值就是用户所选的值，
场景题的分值挂在**选项**上（`question_options.score_map`），而且一个选择会
同时喂给多个维度。这条链路上有四个环节，每一个断了都**不会报错**：

| 环节             | 断掉的表现                                | 这一步怎么接                                               |
| ---------------- | ----------------------------------------- | ---------------------------------------------------------- |
| ① 抽题 select    | 少取一个字段 → 该维度恒 0 分              | 加上 `scoreMap` / `feedback` / `scenarioPrompt`            |
| ② 试卷快照       | 快照不固化分值 → 算分时永远是 null        | 快照升 `ps-v2`，选项带 `scoreMap`，题目带 `scenarioPrompt` |
| ③ 引擎按维度累加 | 只算题目声明的那个维度 → 一题只测一个维度 | 按**所选选项实际出现的维度**逐个累加                       |
| ④ 下发给客户端   | 算分依据 = 答案键，被公开                 | 响应里**投影掉** `scoreMap`，快照里保留                    |

第 ④ 条是这一步新做的判断（ADR-039 没写）：`scoreMap` 是**评分键**，
下发等于把"选哪个能得高分"交给客户端。本项目没有"正确答案"，
但把评分键暴露出去会让人去凑分，而凑出来的画像不再是测量结果。
顺带它也是纯负担 —— 52 题 × 4 选项各带一个映射，客户端一次都用不到。

### 16.2 实现中发现、并当场修掉的两个"静默错误"

**① 所有选项同分 → 全维度满分**

`resolveScale` 的第二级（由选项分值推导量程）原先要求 `min < max` 才采用，
否则退回题型默认量程 `FORCED_CHOICE: 0–1`。于是一个**写错的选项分值**
（例如某维度的两个选项都给 3）会走成这样：

```
量程退回 0–1 → clamp(3, 0, 1) = 1 → 该维度恒为 100 分 → 所有人的画像被整体抬高
```

改法：允许返回退化的 `{min, max}`（min === max）。零信息如实传下去 ——
`normalizeToUnit` 对退化量程返回 0、累加器的 `weightedMax − weightedMin` 也是 0，
最终 `usable = false`，该维度**不出结论**（中位 50 仅作占位）。
这正是"没有数据就不该有结论"应有的表现。
对既有量表题零影响（它们的选项没有 `scoreMap`，第二级根本不适用）。

**② 探针的题库太薄 → 提交 500**

场景题冒烟第一版只写了 2 道题、覆盖依恋与冲突两个族，提交直接
`500 / 40016`。查下来**实现是对的**：情感提交在三个族里任何一个给不出结论时

### 17.3 内容层面发现的硬约束：**同场景内选项的维度键必须一致**

第一版题库被覆盖率单测直接拦下，两类问题：

| 问题                      | 后果                                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 某维度只出现在 1 个选项上 | `resolveScale` 要求"全部选项都带该维度"才用选项分值推导量程，部分覆盖会退回题型默认量程 `0–1`，而分值可能是 4 → `clamp(4,0,1)=1`：**该选项直接顶到满分**，且不报错 |
| 各选项的维度键集合不同    | 引擎按**所选选项**里出现的维度累加 → 选 A 的人有 `LOVE_TOUCH` 数据、选 B 的人没有 → **两人的画像无法比较**                                                         |

两条都不是"格式问题"，而是会让分数静默失真的规则，因此写成了单测断言：
**同场景内所有选项的键集合完全一致**，且每个维度在同一场景内至少有 2 个不同取值
（否则该维度零信息）。

覆盖率断言（每套题、逐维度）：**≥4 个选项命中**、**≥3 个不同场景**。
依据是场景题一次作答只贡献一次数据 —— 量表题 52 题里每维度 4 题是结构保证的，
场景题不是，缺了不会报错、只会在报告里悄悄变差。

## 19. 2026-10-15：ADR-039 第五步 —— 沉浸式答题页

### 19.1 没有另开页面，而是在同一页做两套排版

场景题与量表题在**数据侧**是同一个结构（题干 + 若干选项），差别只在呈现：
量表题干是一行陈述，场景是一段处境 + 提问 + 选完的一句反馈。因此答题页
**沿用同一个页面**，按 scenarioPrompt 是否存在切换分支。

这么做不是图省事：断点续答、漏答补救（"还有 N 题未作答 · 去补答"）、
进度条、返回键、自动跳题的取消逻辑 —— 这些**只有一份实现**。
另开一个页面等于把它们各写一遍，而其中"自动跳题的取消"正是上次静默漏答的根因，
复制一份迟早会漏掉一处。

### 19.2 三处专为沉浸感做的调整

| 调整                   | 做法                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------- |
| **处境与提问分开排版** | 叙述放进独立卡片（更大行距与内边距），提问单独一行加粗 —— 先"进入场景"再"看到问题" |
| **进度用"幕"**         | 场景题显示「第 N 幕 / 共 24 幕」而不是「第 N 题」—— 它是叙事，不是卷子             |
| **反馈要读得完**       | 选完做法后先显示即时反馈，**延时从 220ms 提到 1400ms** 再滑入下一幕                |

最后一条是这一步唯一"有技术含量"的地方：反馈只有十几个字，
但 220ms 一闪而过等于没有 —— 那样整个反馈功能就白做了。
createAutoAdvance 因此支持**按次覆盖延时**（默认仍 220ms），并补了两条单测
（覆盖后仍然只跳一次、仍可被取消）。

小程序 **vue-tsc 0 + vitest 19 套 254 例**（+2 例：按次覆盖延时）/ uild:mp-weixin 成功
（产物里已生成 quiz__scene / quiz__prompt / quiz__feedback 与「幕」文案）/
prettier 干净。后端未改动。

## 20. 2026-10-15：ADR-039 第六步 —— 报告按性别

### 20.1 性别只影响**例子**，不影响**结论**

用户要求"报告也按性别出"。但测量结论本身不能按性别变：同一份依恋焦虑分数
在男女身上是同一个分数，MBTI 类型也不会因为性别换个字母。一旦让性别参与结论，
报告就从"测量结果"变成"社会角色期待" —— 既不准，两版的分数量纲也不再可比。

因此新增 gender-context.util.ts，把性别限缩成**语境**，只准影响三件事：

| 允许                     | 做法                                                           |
| ------------------------ | -------------------------------------------------------------- |
| 举例与称呼               | 男生 → 「你和她」「你女朋友」；女生 → 「你和他」「你男朋友」   |
| 处境的选取               | 举的例子要贴用户真实会遇到的情形（情感报告尤其明显）           |
| **禁止刻板印象**（强制） | 显式写死"不写『男生不该……』『女生都……』，也不要把性别当作解释" |

未提供性别（UNKNOWN / OTHER / 选「不想说」）→ 一律中性措辞（「对方」「TA」），
并**明确要求不要假设、不要询问、不要提及性别**。
⚠ 这条比"留空"重要得多：报告里冒出一句"作为女生……"对选了「不想说」的用户是直接冒犯。

### 20.2 变量**永远可用**，不走占位文案

`{{genderContext}}` 用直接赋值而不是 `resolve(...)`：未提供性别时给出的是
**一句明确指令**，不是「（本次测评未包含此项）」。后者会让模型自行脑补一个性别。
单测里专门断言了"任何取值都返回可用文本、且不含占位字样"。

### 20.3 硬约束在**模板**里也写一遍（这是本轮唯一一次"故意重复"）

`{{genderContext}}` 的文本由代码生成，而模板是**版本化、可评审、运营能在后台改**的那一份。
第一版只把禁令放在变量里，探针当场发现"模板正文里看不到这条红线"——
谁改了模板、或变量文本被误改，都不会有人立刻发现。
因此模板的「写作语境」块里额外写了一句静态禁令。多几行 token，
换的是评审时它就在眼前。

### 20.4 验证

| 手段                               | 结果      | 覆盖                                                                                                                                                                   |
| ---------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| .runlogs/probe-report-gender.cjs   | **12/12** | 三个模板的 ACTIVE 版本都带 `{{genderContext}}` 与静态禁令；**真实 LLM** 下女生用户的人格报告（6 段）与情感报告（6 段）都生成成功；改性别后画像类型与分数**逐字段不变** |

| 全量门禁                           | 通过      | tsc 0 / eslint 0 / **jest 131 套 3051 例** / 小程序 vue-tsc 0 + vitest 19 套 254 例 / prettier 干净 / /health/ready 200                                                |

**为什么"生成成功"本身就是证据**：渲染器在**任何占位符拿不到变量时会直接抛错**

说明这个变量确实被提供了 —— 不需要去猜模型写了什么。

人工抽样（女生用户的情感报告正文）确实用了「他」：
「……不太容易反复担心「**他**是不是不爱我了」……」——
性别语境进了提示词，模型也照做了。

页面全白。看起来像"代码写崩了"，其实是**产物半新半旧**。

### 21.2 判据：看时间戳，不要看代码

`dist/dev/mp-weixin` 里：

| 文件               | 时间戳          |
| ------------------ | --------------- |
| `app.js`           | 15:38（新）     |
| `common/vendor.js` | **10-13（旧）** |

`app.js` 是新的、它 require 的 vendor 包还是三天前的 —— 于是模块解析不到。
**"app.js 与 common/ 的时间戳不一致"就是这类故障的指纹**，
比读控制台报错快得多。

### 21.3 根因：两条构建同时跑

后台开着 `pnpm dev:mp-weixin`（监视模式），我又手动跑了 `pnpm build:mp-weixin`。
两者共用同一份 vite 缓存与依赖预打包产物，增量构建互相踩 ——
一个在写 `app.js`、另一个刚把 `common/` 判成"未变化"跳过，
于是写出一个自相矛盾的产物。

⚠ **纪律**：同一个前端工程**同时只能有一条构建命令在跑**。
要手动出包就先停掉监视进程，反之亦然。
（本次还额外清了 `node_modules/.vite`，因为缓存本身可能已被写坏。）

### 21.4 修法与验证

1. 停掉监视进程与所有构建进程；
2. 清 `node_modules/.vite`（`dist/dev` 被开发者工具占用删不掉，也不需要删）；
3. **只跑一条** `pnpm dev:mp-weixin`，它会重写全部产物；
4. 验证三件事：
   - `app.js` 与 `common/vendor.js` 时间戳**一致**（16:03:08 / 16:03:08）；
   - 用脚本扫**全量产物的 require 图**，确认没有指向不存在文件的目标（结果：0 个缺失）；
   - 关键页面产物齐备（`pages/index/index.js` / `pkgTest/pages/quiz.js` /
     `pkgTest/pages/result.js` / `components/GenderOnboarding.js`）。

> 这条值得单列：**白屏的第一嫌疑通常是"我刚改的代码"**，
> 而本次真凶是构建流程。先对时间戳与 require 图做一次一分钟的排查，
> 比逐行 review 刚写的代码快得多，也避免把好代码改坏。

## 22. 2026-10-15：情感报告加厚 —— 「报告太简陋」的两处真因

### 22.1 先取证：用户看到的**不是 AI 报告**

用户原话（做完 24 幕场景测评之后）：

> 沉浸式的题目很好，要提出表扬，但是后面的报告太简陋了……看完这个报告，
> 我甚至不知道想表达什么，信息也不多，也没有告诉我我属于什么，需要什么，
> 给的建议是什么。

第一件事不是改提示词，而是**确认他到底看到了什么**：

```
node .runlogs/inspect-emotion-reports.cjs
→ 库里没有任何 EMOTION_REPORT
```

也就是说：他根本没生成过 AI 报告（报告要用户主动点"生成"才排队），
他抱怨的那一屏是**结果页** —— 只有「焦虑型 / 爱的语言五项分数 / 冲突风格」
三个标签加一段合规免责，**一句解释都没有**。

**这一条改变了修法**：要修的是**两处**，而且结果页那处更紧急 ——
它是 100% 的用户都会看到的一屏，AI 报告只有点了生成的人才看得到。

### 22.2 结果页：确定性结论（0 字 → 729 字）

新增 `backend/src/modules/emotion/emotion-conclusion.util.ts`：**纯函数**，
按画像推出一段结论文本，**不调模型、不落库**。选这个形态的三条理由：

| 理由              | 说明                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------- |
| 立刻有内容        | AI 报告要排队几十秒；结果页必须"提交完就有一屏能读的东西"                              |
| 确定性（ADR-005） | 同一份画像任何时候都得到同一段话；换成模型生成，用户刷新一次结论就可能变，反而像在胡说 |
| 可穷尽测试        | 文案是表驱动的，红线可以逐条断言，而不是"抽一份报告人工看看"                           |

输出字段（`EmotionConclusion`）：`headline`（一句话）`portrait`（两轴解读）
`needs`（我最需要什么）`conflict`（争执里我怎么办）`strengths[]`（3 条）
`suggestions[]`（3 条）`note`（合规提示）。

内容表：4 种依恋类型的 `headline`、5 种爱的语言的"需求句"、5 种冲突风格句、
依恋类型 × 爱语的建议组合。**只有表里有的说法才会被输出**，
因此"给建议"这件事也被限定了范围：只给**行为层面**的建议（例如把
"你是不是不高兴了"换成"我想抱一下"），不给临床建议、不裁决关系。

红线由 `emotion-conclusion.util.spec.ts` 钉住：禁临床词（诊断/症状/障碍/治疗）、
不出现"你们不合适/这段关系没救了"这类裁决、四种类型画像句**互不相同**
（防复制粘贴式糊弄）、同一输入永远同一输出。

实测（用户真实画像：焦虑 52.38 / 回避 0 / 触碰 63.16 / 精心时刻 62.07 /
服务 4.55 / 协作 100）：输出 **729 字**，其中最有价值的一句是它自己算出来的 ——

> 相比之下，「服务的行动」对你几乎不起作用——不是你不领情，
> 而是它替代不了你真正需要的那个确认。

这句不是写死的文案，是"主导爱语 vs 最低分爱语"两条数据碰出来的结论。

其余改动：

### 22.5 这一轮踩到的三个坑（都不在业务逻辑里）

1. **`change_note` 是 `VarChar(512)`** —— v3 的变更说明写长了一百多字，

   让它在**测试**里失败，而不是在灌库那一步。
2. **探针把 `scenarioPrompt` 当成了情境** —— 实际情境在 `content`，
   `scenarioPrompt` 是提问行（实测 9–13 字，如"这一刻你更想要的是？"）。
   断言写成 `scenarioPrompt.length > 10` 于是判红，而红的原因是**断言错了**，
   不是实现错了。
3. **探针里的字段名靠记忆写** —— `EmotionProfile` 是 `attachmentAnxiety`
   （不是 `anxietyScore`）、`AiUsageLog` 是 `costAmount` / `latencyMs`

   探针脚本没有类型检查，这类错只能在运行时以 `PrismaClientValidationError` 暴露，
   每次都要多跑一轮。**探针里凡是查库，字段名一律回 `schema.prisma` 里抄。**

另有一处**文档损坏**值得记一笔：§20.4 表格里混进了一个同形异义字符
（`attachmentAxes` 的 `a` 位置上是西里尔字母），肉眼完全看不出，

最后只能按行定位 + 整行重写。**结论：中文文档里的替换要按行做，不要靠字符串匹配。**

## 23. 2026-10-15：开一个开发会员，撞出「`memberships` 表只读不写」

| 表             | 谁在读                                                                                                                                                                                          | 谁在写                                                     |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |

检索方式（排除 spec）：全仓搜 `membership` 且行内含 `create|upsert|insert` → **零命中**；

- `refund.service.ts` 退款时同步取消会员实例（`updateMany`）；
- `admin-user.service.ts` 后台封禁补偿时给会员延期（`update`）。

**一个旁证**：退款里那段"同步取消会员实例"的注释写着
「`memberships` 与 `entitlements` 是两份表达，只改一份会留下矛盾数据」——
写这段的人**假设会员实例存在**，而实际上它永远不会被创建。

### 23.3 用户可见的后果（付费墙本身没问题）

先说清楚：**付费墙是好的**。`entitlement.util.ts` 只读权益（ADR-015：权益是解锁付费内容的

1. **「我的」页**（`GET /users/me?include=membership`）：买完会员仍显示"未开通"；

## 24. 2026-10-15：报告详情页改版 —— 「全是字」这件事怎么修

### 24.1 用户原话与判断

> 我看到了，然后我点击了我的报告，有一份情感测评报告对吧，然后点开一看，哇，全是字，
> 我是用户我看都不想看，累不累啊，最好是图文并茂，一针见血，显得有亲和力，
> 而不是字多就行。

先确认这不是"内容不够"的问题：上一轮他刚说过「信息也不多」，本轮改成 6 段 3706 字。
两句话并不矛盾 —— **上一轮缺的是信息，这一轮缺的是"读得下去的路径"**。
因此本轮**不动内容**（一个字都没删），改的是版式与阅读顺序。

### 24.2 版式：三段式，先给结论再给深读

| 位置       | 内容                                                           | 给谁看             |
| ---------- | -------------------------------------------------------------- | ------------------ |
| ① 首屏     | 一句话（确定性结论的 `headline`）+ 段数 / 时长 / 模型          | 3 秒知道在讲什么   |
| ② 数据卡   | 依恋双轴（带判定中线）、五项爱的语言、五种冲突风格（主导高亮） | 一眼看到"我是谁"   |
| ③ 结论卡   | 「你最需要什么」+ 3 件立刻能做的事 + 合规提示                  | 想拿走可执行的东西 |
| ④ 六段正文 | 每段**首句放大**、其余折叠；建议段拆 5 张卡、行动段拆两周两块  | 想深读的人         |

改动前那 3706 字是"一整段一整段铺开"（`<text>` + `white-space: pre-wrap`），
「五条建议」一段 968 字直接压在屏幕上 —— 这就是"一堵墙"的来源。

### 24.3 后端：新增 `profileSnapshot`（画图要有数据）

报告正文里本来就写满了数字（「焦虑轴 52、回避轴 0」「身体的接触 63、精心的时刻 62」
「服务的行动 5」），它们是最有说服力的部分，却全埋在句子里。因此
`GET /reports/{id}` 新增一个**纯新增**字段 `profileSnapshot`：

- `kind = 'EMOTION'`：两轴数值 + 判定阈值 + 五项爱语 + 五种冲突 + **确定性结论**；
- `kind = 'PERSONALITY'`：`mbtiType` + 四维百分比 + 大五；
- 无画像（关系 / 成长报告）→ `null`。

三条边界（都写进了契约 §3.5.3 与 `report-profile-snapshot.util.ts` 的头注释）：

1. **不参与付费墙判定**：它描述的是"你的画像"（结果页早就给用户看过），
   不是"报告写了什么"；被锁的始终是 `sections[].content`。
   探针里专门有一条断言：快照的 JSON 里不含任何未解锁段落的正文。
2. **只发编码不发中文标签**（`ANXIOUS` / `LOVE_TOUCH` / `CONFLICT_*`）：
   标签的唯一来源仍是前端 `config/modules.ts`，与结果接口同一口径。
3. **取报告绑定的那份画像**（`emotionProfileId` / `profileId`），**不是用户当前画像**：
   用户后来又测了一次、画像升到 v2 之后，这份报告仍应展示当初那份数值 ——
   否则报告正文写着"焦虑 52"，页面上的条形图却是新画像的 71。

`conclusion` 走的是**与结果页同一个纯函数**（`buildEmotionConclusion`），
探针里逐字比对了两处的 JSON：同一份画像在结果页与报告页必须是同一段话。

### 24.4 前端：版式解析是纯函数，且**失败只能降级不能丢字**

新增 `frontend/miniapp/src/pkgReport/report-content.ts`（纯函数 + 17 例单测）：

| 解析                                      | 依据                           | 失败时       |
| ----------------------------------------- | ------------------------------ | ------------ |
| 按空行切段                                | 模型输出两段之间必有空行       | 退回整段     |
| 再按单换行切（兜底）                      | 每行都 ≥ 24 字才算"其实是分段" | 退回整段     |
| 首句（放大）                              | 模板要求每段首句直接给结论     | 退回整段开头 |
| 建议卡（`1.`–`5.`，**含 `**1.**` 写法**） | 模板硬性要求编号               | 退回普通段落 |
| 两周块（`第一周` / `第 1 周` 都认）       | 模板硬性要求按两周排           | 退回普通段落 |

两条硬约束写在测试里：

- **`lead + paragraphs` 拼回去必须与原文逐字相同**（首句只是被"提"出来，不是被删掉）；
- **卡片正文按顺序拼回去必须覆盖原文**（拆卡不丢字）。

页面组件：`components/ReportProfileChart.vue`（数据卡）与
`components/ReportSectionCard.vue`（段落卡）—— 两者都只做展示，
解析全在纯函数里，因此版式规则可以穷尽测试，而不是"上真机点点看"。

### 24.6 这一轮踩的坑：**两条断言写错，而不是实现错**

1. **「快照里不出现中文标签」判红** —— 实现是对的：`conclusion` 是给用户读的**中文散文**
   （"你最需要的是「身体的接触」……"），当然含中文标签。规则的真正范围是
   **结构化字段**（编码 + 数值），断言要排除 `conclusion`。
2. **单换行兜底的阈值取 40 太高** —— 实测模型写的段落行常在 25–35 字
   （"你的两条轴也说明了这一点。焦虑轴 52、回避轴 0……"），阈值过高会让报告
   **切不开段**，而"切不开段"在页面上就等于回到了那堵墙 —— 恰好是这个改动要解决的问题。
   已降到 24，并把理由写进注释。
3. **「第 1 周」阿拉伯数字写法** —— 模板写的是"第一周"，模型偶尔写"第 1 周"，
   只认一种时另一种就解析不出来（不丢内容，但版式退化）。已两种都认并归一成"第一周"。

## 25. 2026-10-15：心理状态自评改版 —— 「这两周的一天」（24 幕情境）

### 25.1 用户拍板的三件事

> 下一步做心理状态自评，测评方式同样取消这种普通的问卷作答，改用别的方式。

我给了五个方向并说明取舍（时间轴情境化 / 卡片滑动 / 一周日历 / 身体信号点选 /
AI 对话访谈），用户选了：

| 决定     | 选择                                                     |
| -------- | -------------------------------------------------------- |
| 作答形式 | **「这两周的一天」时间轴情境化自评**（6 个时刻 × 4 幕）  |
| 附加环节 | 一周节律落点 + 身体信号点选（**不计分**，见 §25.6 待办） |
| 旧量表   | **删掉，改用全新的**                                     |

### 25.2 为什么这个模块不能照抄情感模块的改法

情感测的是**风格偏好** —— 怎么问都不影响"准不准"，所以那轮可以放开手做沉浸式。
本模块的六个维度（压力 / 情绪 / 紧张 / 睡眠 / 精力 / 缺少支持）与 PHQ-9、
GAD-7 这类筛查量表重叠，**它必须仍然是一个可信的自评**。

因此这次改的是**问法**，不是**尺子**：

| 保持不变                                        | 换掉的                  |
| ----------------------------------------------- | ----------------------- |
| 六个维度、每维 4 题（2 正 + 2 反）              | 抽象自评陈述 → 生活情境 |
| 四档作答、分值挂在选项 `scoreMap` 上（1–4）     | 李克特 5 点 → 频率四档  |
| 反向计分（`min + max − value`）、一致性评分口径 | 逐题选项 → 全卷统一四档 |
| 档位阈值（30 / 50 / 70）、整体档位、结论文案    | —                       |

24 幕按一天的时间轴排开：**早上醒来 → 出门通勤 → 白天做事 → 跟人相处 →
晚上一个人 → 躺下之后**。例（第 21 幕）：

> 关灯躺好，脑子却开始转：白天说错的那句话、明天可能出的岔子。越想越清醒。
> **这两周，这样的夜里大概有多少？**
> 几乎没有 / 有那么两三天 / 一半以上的日子 / 几乎每天

### 25.3 技术上是"白捡"的（基础设施上一轮已经建好）

| 需要的能力            | 现状                                                      |
| --------------------- | --------------------------------------------------------- |
| 试卷下发情境 + 提问行 | `scenarioPrompt` 已在通用抽题查询与快照里（ADR-039 建的） |
| 选项级算分            | `computeEffectiveValue` 已支持 `scoreMap` + 维度参数      |
| 反向计分              | 引擎本来就按 `question.reverseScored` 算                  |
| 答题页渲染情境卡      | 沉浸式答题页按 `scenarioPrompt` 分支，**一行都没改**      |

也就是说：题库换掉之后，**引擎、答题页、结果页、提交链路全部不动**。

### 25.4 🔴 但发现一个会让改版白做的问题：**试卷默认是乱序的**

第一次跑探针时，第一幕的提问行是「这样的**夜里**大概有多少？」而不是"早晨" ——
一查 `buildPaperSnapshot(questions, { audience })`：`shuffled` **默认为 `true`**。

乱序对量表题是**对的**（打散"同一维度连着问"的作答定势），但对一条叙事是灾难：
用户会从"躺下之后"跳回"早上醒来"，**沉浸感直接归零，而这正是这次改版的全部意义**。

修法：在 `test.service.ts` 加一条**按模块**的规则

```ts
const NO_SHUFFLE_MODULES: ReadonlySet<string> = new Set(['MENTAL_HEALTH']);
```

默认（未列出的模块）保持乱序、与既有行为一致；新增模块若要保序必须显式登记并说明理由。
单测一正一反把规则钉住（`PERSONALITY` → `shuffled: true`；`MENTAL_HEALTH` → `false`），
探针里也加了"24 幕按 `MH_SC_01 → MH_SC_24` 顺序下发 + 首幕是早晨、末幕是躺下之后"。

> 这条值得记：**题库设计得再好，也可能被一个默认参数悄悄抹掉**。
> 如果只在编辑器里读题库、不跑一次端到端，这个改版上线后会"看着像新功能、
> 用起来还是乱跳" —— 而且没有任何报错。

### 25.5 一个更隐蔽的坑：`order` 并列（顺手修掉）

旧题库的 `order` 是"维度内 0–3"，六个维度各写一遍 → **大量并列**，
试卷顺序取决于数据库对并列行的返回次序（没有保证）。
新题库改成全局唯一连续 0–23，并在灌库阶段断言（`orders.size === scenes.length`），
把"顺序不确定"变成灌库即失败。

### 25.6 守住的四条约束（都在 `questions.mental-health-scenes.spec.ts` 里）

1. **反向题方向逐题写死**：`reverseScored` 写反不会报错，只会让该维度**静默反向**
   —— 状态最差的人拿到最低分，而结论文案读起来毫无破绽。因此 spec 里有一张
   24 行的期望方向表，**不靠推算，靠人工确认**；改了题面就必须来改表。
2. **反馈不含建议**：本模块的产品形态是"只做状态描述、不给建议、不做干预"。
   一句"试试早点睡"读起来很贴心，但那就是破线。spec 断言四档反馈都不含
   建议性措辞，端到端探针则把**整份卷面文本**（题干/提问/选项/反馈）一起扫。
3. **不做性别分卷**（ADR-039 ⓕ）：24 幕 `audience` 一律 `ALL`。
   恋爱处境确有性别角色差异，近两周的压力、睡眠、精力没有 ——
   按性别分开问反而在暗示"某个性别更容易出问题"。
4. **提问行必须带"这两周"**：少了时间窗，用户会按"最近一天"或"一直以来"作答，分数不可比。

## 26. 2026-10-16：心理评测结果页重做 —— 「没特色、没建议、看不出所以然」+ 顶部被遮挡

### 26.1 用户的两条反馈

> 心理评测报告没有特色，没有建设性建议，我看不出个所以然来，请你结合市面上类似的
> 程序或者应用，结合一下长处来设计评测报告所展示的内容；
> 然后评测报告的 UI 请整体往下移动，已经被手机的上端遮挡了。

第一条是**内容设计**（本轮主体），第二条是**真 UI 缺陷**，两者互不相关，分开修。

### 26.2 🔴 顶部被遮挡：一处"只在某个页面初始化"的默认值

**现象**：自定义导航栏的标题与返回按钮被状态栏/刘海压住。

**根因**：`pages/result`、`pages/quiz`、`pages/index` 都是 `navigationStyle: custom`
（系统不给导航栏），它们靠 `appStore.statusBarHeight` 自己让开状态栏。
而 `initSystemMetrics()` **原先只在首页的 `onShow` 里调用**：

- 正常从首页进入 → 值正确；
- **从分享卡片 / 消息 / 最近使用直接进入子包页面** → 首页从未挂载 →
  `statusBarHeight` 停在默认值 `20`；
- 而真机的状态栏常见 44–59px → 页面内容被顶进状态栏里。

**修法**：初始化挪到 `App.vue` 的 `onLaunch`（**一次且必然发生**），
首页那次保留（横竖屏/分屏后可再校准），并把结果页的导航栏内边距从
`statusBarHeight` 改成 `statusBarHeight + 8`（只加状态栏高度时标题正好贴在下沿，
视觉上像被"顶住"）。

> 这类缺陷的共性是：**它取决于用户从哪儿进来**，所以在开发者工具里从首页点进去
> 永远复现不了。凡是"全局只算一次的量"（系统尺寸、时区、环境判断），
> 初始化位置就必须在 `onLaunch`，不能挂在某个页面上。

### 26.3 内容重做：对照市面做法，四个问题都要有答案

改版前那一屏只有：整体档位一句话 + 六条分数 + 一段三句话的结论 + 免责声明。
**分数有了，含义没有；结论有了，下一步没有。** 对照市面上的自评类产品
（Woebot / Wysa 一类用呼吸、正念、接地等技术做即时干预；
UCLA Health 等机构科普则强调**规律作息**这类日常惯例的价值），
一份说得过去的自评结果至少要回答四个问题：

| 用户的问题           | 市面常见做法            | 本轮的答案（规则生成，非 AI）                   |
| -------------------- | ----------------------- | ----------------------------------------------- |
| 这个分数是什么意思？ | 每维配一句人话解释      | `readings`：每维"在测什么"+"偏高时的常见体验"   |
| 只有我这样吗？       | 去污名化的一句          | `endorsement`：按整体档位给不同措辞             |
| 我现在能做什么？     | 2–3 条当天可做的小事    | `suggestions`：做什么 + 为什么有效 + 什么时候做 |
| 什么时候找人聊聊？   | 分档求助指引 + 官方热线 | `support`：三档都给，附 **12356**               |

再加两件"特色"：**只看最值得留意的 2 项**（六条平铺等于没有重点）与
**两周后再测一次**（单次分数只是快照，趋势才有意义）。

参考来源：[全国统一心理援助热线 12356（国家卫健委）](https://www.gov.cn/zhengce/zhengceku/202412/content_6994470.htm)、
[国家心理健康和精神卫生防治中心](https://ncmhc.org.cn/channel/newsinfo/7902)、
[Wysa/Tess 的结构化减压技术（JMIR）](https://preprints.jmir.org/preprint/78340/submitted)、
[规律日常惯例与心理健康（UCLA Health）](https://www.uclahealth.org/news/article/how-daily-routine-can-boost-your-mental-health)。

### 26.4 与「只做结论、不建议」那条红线的关系：**明确收窄，不是取消**

本模块原先的形态是「只做结论、不给建议、不做心理干预」。那条红线的**真正目的**
是不做**临床建议与心理干预**，而不是"一个字都不许说"。因此本轮把边界重新写清：

| 允许                                                     | 禁止                                         |
| -------------------------------------------------------- | -------------------------------------------- |
| 生活层面的自我照顾（记录、呼吸、规律作息、出门、找人说） | 临床建议、提药物、提治疗、承诺疗效           |
| "最近压力感比较明显时，可以……"（描述处境）               | "你患有……，应该……"（基于"病"说话）           |
| 分档的**求助指引** + 官方热线                            | 替代专业判断（"你不需要看医生"这类反向引导） |

四条边界都有断言：`mental-health-report.util.spec.ts` 扫描全部用户可见文案
（含建议、求助、去污名化），端到端探针另外把**解读层**与**整份卷面**一起扫。

### 26.5 顺带修掉一个"结论与分数打架"的缺陷（用户"看不出所以然"的真正来源）

预览时发现：故意答出「睡眠 100、紧张 100、其余四项 0」，页面上写着
**两项"比较突出"**，而整体档位却是**「整体比较平稳」** —— 因为整体档位只看六维均值
（33.3 < 35 → GOOD）。

这正是"看不出所以然"最典型的成因：**结论与眼前的分数互相矛盾，用户不知道该信哪个。**
已改成"均值档位"与"单项档位"**取较高者**：

- 任一项 ≥ 70 → 整体至少「有些起伏」；
- 两项以上 ≥ 70，或单项 ≥ 85 → 整体「有几处值得留意」。

均值仍然下发（`overallScore`），只是不再单独决定档位措辞。
规则与阈值一起写进 `resolveOverallLevel` 的头注释，并补了 6 条单测
（含"`usable: false` 的占位分不抬高整体"）。

### 26.6 顺手抓到的两处文案缺陷（都是实测预览时才看见）

1. **Markdown 标记混进纯文本**：求助文案里写过 `**建议找专业人士聊一次**`，

## 27. 2026-10-16：AI 管家「对话框拖不动，像卡死了」—— 根因是两行 CSS

### 27.1 反馈与第一判断

> 刚才我测评了一下 AI 管家，她是能回答的，但是对话框我没有办法拖动，就像卡死了一样。

"能回答"说明**接口、会话、配额都是好的**，问题在渲染层。而"卡死"这个描述很关键：
不是"内容显示不全"，而是**手指怎么拉都不动**。

### 27.2 根因：`scroll-view` 只有 `flex: 1`，没有确定高度

聊天页的消息流是全仓**唯一**的竖向 `scroll-view`：

```html
<scroll-view class="chat__body" scroll-y :scroll-into-view="scrollIntoView">…</scroll-view>
```

```scss
.chat {
  display: flex;
  flex-direction: column;
  height: 100vh;
}
.chat__body {
  flex: 1; /* ← 问题在这里 */
}
```

而这一页在 `pages.json` 里是 **`disableScroll: true`**（页面级滚动关闭：
输入框要固定在底部、列表自己滚）。于是：

1. `scroll-view` 竖滚**必须有确定高度**（微信官方要求给固定 `height`）；
2. 只写 `flex: 1` 时，flex 项的自动最小尺寸是**内容高度**（`min-height: auto`）——
   消息一多，这个盒子就长到跟内容一样高，它内部**没有可滚的区域**；
3. 页面级滚动又是关的 → **两边都滚不动**，表现就是"卡死"。

短对话时完全正常（内容没超过一屏），**只有回复足够长时才出现** ——
这类缺陷最容易在自测时漏掉。

### 27.3 修法

```scss
.chat {
  height: 100vh;
  overflow: hidden;
} /* 溢出只允许发生在列表内部 */
.chat__body {
  flex: 1;
  height: 0;
  min-height: 0;
}
```

- `min-height: 0` 允许它缩到比内容更小；
- `height: 0` 让高度**完全由 flex 分配**决定（只写其中一个，部分机型上仍会被内容撑开，
  因此两个都写）；
- 根容器 `overflow: hidden` 与 `disableScroll: true` 配套：页面既然滚不动，
  溢出就必须裁掉，否则内容会顶出视口且看不到下半截。

### 27.4 为什么给 CSS 写了一条单测

新增 `tests/pkg-chat/chat-scroll.spec.ts`（4 例）：读 SFC 源码、抽出 `&__body` 的声明块，
要求它同时具备 `min-height: 0` + `height: 0` + `flex: 1`，并断言根容器有
`height: 100vh` 与 `overflow: hidden`、`pages.json` 里该页确实是 `disableScroll: true`。

理由：**这类缺陷类型检查、单测、构建、甚至页面渲染全都发现不了**，
只有"消息足够长"的那一刻才出现；而修复方式只是一行 `min-height: 0`，
后来者"顺手清理"掉也不会报错。这是少数值得用文本断言盯住的样式规则。

> 顺带记一条通用经验：**"滚不动"先看高度是不是确定的**。
> `scroll-view` / `overflow: auto` 的容器，只要高度由内容决定，它就没有可滚区域；
> 而 flex 布局里的 `min-height: auto` 正是"高度由内容决定"最常见的来源。

| 项         | 结果                                                         |
| ---------- | ------------------------------------------------------------ |
| 结构守卫   | `tests/pkg-chat/chat-scroll.spec.ts` **4/4**                 |
| 小程序门禁 | vue-tsc 0 / **vitest 21 套 275 例** / `build:mp-weixin` 成功 |
| 后端       | 未改动（本轮纯前端）                                         |

**仍需真机确认**：长回复时能否上下拖动、发送后是否自动滚到底部
（`scroll-into-view` 用的是每条消息唯一的 `msg-<id>`，值每次都变，因此会重新触发滚动）。

## 29. 2026-10-16：小程序侧「所有接口都 401」—— 两个独立缺陷叠在一起

### 29.1 用户报的现象

开发者工具控制台里 `personality/me`、`reports`、`tests`、`users/me`、`zodiac/signs`
**全部 401**，末尾还有一条 `zodiac/daily` 400。

「**全部** 401」这个特征很关键：它说明请求根本没带上有效令牌，
问题不在某个接口，而在**登录链路**上。

### 29.2 取证：先看服务端发生了什么

新建 `.runlogs/diagnose-401.cjs` 顺着链路查：

| 检查项                  | 结果                                                      |
| ----------------------- | --------------------------------------------------------- |
| 账号状态                | `ACTIVE`、`version=1`、未注销 → **账号没问题**            |
| 最近会话                | **07:38:45 刚签发了两条新会话**，`lastLoginAt` 也是那一刻 |
| `lastUsedAt`            | **「从未」** —— 带令牌的请求根本没到达守卫                |
| 无令牌 / 伪造令牌打接口 | `20000 请先登录` / `20002 登录凭证无效`（符合预期）       |

结论：**登录其实是成功的**（后端确实签发了新会话），但首屏那批请求
在"还没有有效令牌"的时候就已经发出去了。

### 29.3 缺陷一（前端）：续期不可用时没有"重登后重放"

请求层原有的 401 处理是：续期 → 有则重放；否则 `onUnauthorized()` 清会话并抛错。

而实测的故障链里，**续期根本做不了**（storage 里只剩过期的 access token，
refresh token 也没了 —— 重新编译/清缓存后很常见）：

```
① 首屏请求带着过期令牌发出 → 401
② 401 分支尝试续期 → 无可用 refresh token → 返回 null
③ 于是清会话 + 把 401 抛给页面
④ 而 silentLogin 随后其实成功了（服务端日志里的两条新会话就是证据）
⑤ 但首屏那批数据永远不会回来 → 用户看到的就是"全是 401、首页空着"
```

修法：在"续期不可用"这条分支上加**静默重登一次 + 用新令牌重放**，
并用 `relogged` 标记保证每个请求**最多重放一次**（登录本身坏掉时不死循环）。

⚠ 一个关键细节：**重登拿到的令牌必须与原来不同才重放**。
第一版没比这一次，结果把一个既有用例打破了 —— 而那个用例的失败方式很有教育意义：
hooks 是**合并**注册的，前一个用例注册的 `ensureAuthReady` 被沿用，
于是"重登"用一个没变的令牌再打一次，测试里队列已空、mock 返回了**成功**响应，
断言"应当抛错"因此变成"拿到了 null"。这提醒两件事：

- 实现上：令牌没变就用同一个令牌再打一次，除了多一次请求，还可能**把错误掩盖成假成功**；
- 测试上：断言 401 行为的用例必须显式声明"没有重登能力"（`ensureAuthReady: undefined`）。

### 29.4 缺陷二（后端，我自己写的）：公开接口漏了 `@Public()`

`GET /zodiac/signs` 在接口文档里写着"**不需要登录**即可访问"，
但控制器上**没有标 `@Public()`** —— 全局 `JwtAuthGuard` 注册在 `APP_GUARD` 上，
默认拒绝一切未标记的接口，于是它返回 401。`/zodiac/match` 同理（已一并修）。

**为什么探针没测出来**：第一版探针**始终带着令牌**调用所有接口，
于是"未登录能不能读"这条断言根本不存在 —— 测的还是"登录后能不能读"。
已在探针里补**真·无令牌**的三条断言（两个公开接口 200、运势接口仍 401）。

> 教训：**公开接口的测试必须真的不带凭证**。带令牌去测公开性，等于没测。

### 29.5 顺手改掉的一处体验问题

`/zodiac/daily` 在未设置生日时返回 `400 / 30019` —— 那是本模块的**正常流程**
（页面据此展示"先选出生日期"的卡片）。但前端原先没关统一错误提示，
用户一进页面先看到红色报错、再看到引导卡，顺序反了。
已给星座的四个运势接口加 `showError: false`，由页面按错误码自行分支。

## 30. 2026-10-16：星盘与上升星座（ADR-040）—— 以及三个"自证永远发现不了"的天文缺陷

### 30.1 起因

用户的反馈是两句连在一起的话：**「里面的内容还是太简单，然后星盘和上升星座这些呢？
我感觉这些总体都还是不够专业」**。

"不够专业"这件事有一个具体的技术含义：星座运势那一层只用到**太阳星座**（出生日期决定），
而同一个太阳星座的人可以有一万种星盘。要显得专业，就必须真的把出生那一刻的天图算出来：
十大行星的度数、上升点与天顶、十二宫、相互相位、元素分布。

**约束**：不允许引入新的 npm 依赖（本仓库对依赖很克制，天文库动辄几 MB 且多为精度不明的移植）。
因此这一层是自己实现的。

### 30.2 自己实现天文计算，风险在哪里

风险不在于"公式写不出来"，而在于**写错了不会报错**：

- 水星实际在天秤，算成天蝎 —— 页面照样渲染，用户也不知道；
- 上升点算成了**下降点**（差 180°）—— 照样是个合法星座，只有懂行的人能看出不对；
- 行星位置整体偏 0.9° —— 只有恰好压在星座边界上的人会看到错星座。

这类缺陷**单元测试、类型检查、构建、页面渲染全都发现不了**，因为测试里的期望值
如果来自实现自身，那就是自证。所以这一层的验证原则是：
**断言必须来自与被测代码无关的外部事实。**

### 30.3 三类外部锚点 + 一类物理恒等式

| 锚点类型         | 具体                                  | 用法                                                |
| ---------------- | ------------------------------------- | --------------------------------------------------- |
| ① 节气           | 2026 春分 / 夏至 / 秋分（公开到分钟） | 太阳黄经在那一刻必须等于 0° / 90° / 180°            |
| ② 行星换座       | 15 个公开的换座／退回日期（见 30.5）  | 行星必须压在 0°00′ 的星座边界上                     |
| ③ 朔望月         | 2026-01-18 新月                       | 日月黄经差必须 ≈ 0°                                 |
| ④ **地平线物理** | 上升点的方位角与高度角                | 必须高度角 = 0°、方位角在东半圈、之后 1° 在地平线下 |
| ⑤ **日出恒等式** | 日出时刻 = 太阳正好在东边地平线上升起 | 那一刻**上升点黄经必然等于太阳黄经**（与公式无关）  |

### 30.4 缺陷一：上升点算成了下降点（差 180°）

标准公式是 `ASC = atan2( cos(RAMC), −( sin(RAMC)·cos ε + tan φ·sin ε ) )`。
我第一版写成了 `atan2(−cos(RAMC), +(…))` —— **两个分量同时反号，结果恰好转 180°**，
返回的是**下降点**。

它骗过了所有这些断言：

- 「上升点落在 0–360 之间」✅（下降点也是）；
- 「上升点与天顶的黄经距离合理」—— 我当时写的是 `assert(..., true)`，**一条永远为真的假断言**；
- 「同刻不同经度上升点不同」✅（下降点同样随经度变化）；
- 「南半球也在地平线上」✅（东西两侧的点高度角都是 0）。

真正抓住它的是**方位角**：算出来的点方位角 264°，那是**西边**。
修好之后方位角 84.25°，并且日出恒等式把误差压到 **0.000°**。

> 顺带纠正一个我自己想当然的判据：上升点**不等于正东点**。只有天赤道才正好东升西落，
> 黄道与地平圈是斜交的，中纬度上上升点会偏离正东十几度（北京实测偏北 5.75°）。
> 所以断言写成"落在东半圈 + 偏离正东不超过 25°"，而不是"≈ 90°"。

### 30.5 缺陷二：给 1800–2050 的根数表加了不属于它的"长期项"（偏 0.9°）

JPL 那一页有**两张表**：1800–2050 表、以及 3000BC–3000AD 表。
后者配有一组"木星到冥王星平均黄经附加项"（`ΔL = b·T² + c·cos(f·T) + s·sin(f·T)`）。
我用了前者，却把后者的附加项也加上了。

这个缺陷的**症状极隐蔽**：换座仍然照换、相位仍然照成、页面完全正常，
只是行星位置整体偏了不到 1°。发现它的过程是本轮最有价值的一段：

一次端到端预览里，`1995-03-20` 的冥王星显示"射手 0°31′"，而我印象里
"冥王星 1995 年 11 月才进射手"—— 看起来差了一年。但**上个月我刚因为"凭印象"
冤枉过一次正确的代码**（木星进狮子：我记错了日期，代码是对的），所以这次先取证。

于是写了 `.runlogs/verify-planet-ingress.cjs`，拿 **15 个公认可查的换座／退回日期**
逐个对表（含"先探入 → 逆行退回 → 再正式进入"三次边界），结果一目了然：

| 天体   | 实测偏移   | 该附加项的量级   | 去掉后的残差 |
| ------ | ---------- | ---------------- | ------------ |
| 天王星 | **−0.87°** | −0.97°           | **+0.04°**   |
| 海王星 | **+0.67°** | +0.68°           | **−0.01°**   |
| 冥王星 | +0.03°     | ≈0（只有 T² 项） | +0.03°       |
| 木星   | +0.07°     | −0.004°          | +0.07°       |
| 土星   | +0.12°     | +0.013°          | +0.12°       |

**偏移量与附加项一一对应** —— 这才是"根因"而不是"巧合"。
去掉那组附加项后，15 个边界日期的残差**全部收敛到 0.10° 以内**（约 6 角分）。

顺带确认了两件"我记错了、代码是对的"的事，都写进了用例注释，
避免下一个人再去"修"正确的代码：

- 木星 **2026-06-30** 才进狮子（我按 2025 记的）；
- 冥王星 1995 年是"年初先探入射手 → 4 月逆行退回天蝎 → 11 月正式进入"，
  所以 1995-03-20 在射手 0°31′ 是**正确**的。

### 30.6 产品判断：两处"宁可不给，不给错"

这两条不是技术细节，而是会直接影响用户信任的取舍，都写进了代码注释与用例：

1. **没有出生时间 → 不出上升星座与十二宫。**
   上升星座约每 2 小时换一个，一天之内十二个星座全都会轮到。
   市面上不少产品在用户没填时间时"默认中午 12:00"照样输出一个上升星座 ——
   那个答案对**大多数用户都是错的**，而用户无从察觉。
2. **没有出生城市 → 同样不出四轴。**
   这一条更隐蔽：上升星座取决于**当地**星空（经度通过恒星时生效），
   中国横跨东经 73°–135°，东西两端地方时相差 4 个多小时。
   若默认按北京算，乌鲁木齐出生的用户上升点会**错整整一个星座**。

对应地，`moment.latitude` 在缺城市时返回 `null` 而不是某个默认值，
并下发 `noPlaceNotice` 说明**为什么必须要城市**（而不是含糊地让用户"填一下"）。

⚠ 一个必须分清的语义（探针第一版就在这上面栽了）：

- **猜**（禁止）：用户从没提过城市，却按某个默认城市算；
- **补齐**（正确）：用户**明确说了**城市名（"乌鲁木齐"），我们从内置城市表查出经纬度。

因此"清掉经纬度但保留城市名"时，星盘**照常算出来**（`placeResolvedFrom = CITY_TABLE`）；
要真正表示"不知道出生地"，必须连城市名一起清。

### 30.7 缺陷三：城市表的标准时区把夏令时判定跳过了（同一人差 12°）

上一条的兜底路径刚上线，端到端探针立刻抓到：**同一个人的同一份出生信息**
（1988-07-15 14:30 北京），

- 走"存过经纬度"→ 上升点 **天蝎座 3°34′**；
- 走"只存了城市名，坐标由城市表补齐"→ 上升点 **天蝎座 15°24′**。

差 12°，而两条路都自称北京。

根因：最初 `resolveTimezoneOffset` 把传入的偏移当成"最终值"、**给了就直接返回**。
城市表里北京存的是标准时区 **+8**，于是中国 1986–1991 年的夏令时判定被整个跳过 ——
而 1988-07-15 正处于夏令时窗口（+9）。少算 1 小时，上升点差约 12°。

修法是把语义拆开：`baseOffset` 只表示**标准时区**；
**只要标准时区是 +8（即中国），就按公布窗口叠加夏令时**，不管这个 +8 是用户填的
还是城市表给的；其他标准时区（东京 +9）不适用中国规则，避免多加 1 小时。

> 这正是我在 30.6 里警告过的那类风险（"1 小时的误差足以让上升星座落到前一个星座"），
> 结果在我自己的新代码里以另一种形式复现了。它能被抓到，只因为探针里有一条
> **"两条路径算出的上升点必须完全一致"** 的断言 —— 单测永远想不到去比这个。

## 31. 2026-10-16：星盘页实测「选城市时白屏」+ 控制台 method "false"（用户报）

### 31.1 用户报的现象

> 「我点击我的星盘跳出让我选城市，但是页面只有白屏啊」

控制台另有两行：

```
Component "pkgZodiac/pages/chart" does not have a method "false" to handle event "tap".
```

### 31.2 两个症状、两个不同的根因

**根因一：`@tap` 里写了裸赋值语句。**

```html
<!-- 错 -->
<view class="chart__mask" @tap="cityPanelOpen = false"></view>
```

微信编译器会从事件表达式里**提取一个"方法名"**：方法引用（`@tap="saveTime"`）取 `saveTime`，
方法调用（`@tap="pickCity(city)"`）取 `pickCity` —— 都正常；而裸赋值语句
`cityPanelOpen = false` 被取成了 **`false`**，于是运行时去找名为 `false` 的方法，
报出上面那条错误。

编译产物是最好的证据（`dist/dev/mp-weixin/pkgZodiac/pages/chart.js`）：

```
aj: common_vendor.o(($event) => cityPanelOpen.value = false, "3a")   ← 报错的那一个
ai: common_vendor.o(() => { })                                        ← @tap.stop 生成的空处理器（正常）
```

**根因二：面板里的城市列表高度为 0 —— 这才是"白屏"的真身。**

面板是绝对定位的底部弹层，第一版只写了 `max-height: 70vh`（高度由内容决定），
而列表是竖向 `scroll-view`，我给它写的是 `height: 0; flex: 1`：

```
max-height: 70vh（父级高度不确定）
  └─ scroll-view { height: 0; flex: 1 }   ← flex 没有可分配空间 → 高度 0
```

聊天页能用同一套写法，是因为它的父级有**确定的 flex 高度链**；
这里是绝对定位面板，必须自己把高度定下来。用户实际看到的就是：
遮罩盖住整页 + 一个只显示「选择出生城市」和输入框的白框，其余一片空白。

修法：面板改成**确定高度** `height: 62vh`，列表用 `flex: 1; min-height: 0`。
顺带补了标题栏的「关闭」入口 —— 原来只能点遮罩关闭，而那个入口恰好就是报错的那一行。

### 31.3 顺手加的一条兜底

星盘页是这个模块里唯一"必须看到内容"的页面，因此给 `v-if` 链补了一个兜底分支：
拿到响应但既没有 `chart` 也没有 `preview` 时，给一句「星盘暂时取不到 + 重新加载」，
而不是把页面留成空白。任何分支下都必须有可见内容。

### 31.4 ⚠ 一个必须说的教训：**检查不全的守卫比没有守卫更危险**

我给这两个坑写了结构守卫（`tests/pkg-zodiac/chart-page.spec.ts`），第一版**全部通过** ——
而当时的代码里明明就有那个 bug。原因是守卫里的模板切片写成了：

```ts
source.slice(source.indexOf('<template>'), source.indexOf('</template>'));
```

本页用了**嵌套** `<template v-else-if>`，第一个 `</template>` 出现在页面中部，
于是切片在页面下半部分之前就断了 —— 而城市面板恰好在最下面。
**守卫"通过"了，但它根本没检查到出问题的那一段。**

修正为 `lastIndexOf('</template>')` 之后，并且**把 bug 临时塞回去验证守卫会变红**
（确认 `cityPanelOpen = false -> false` 这一条会失败），才敢说这条守卫是有效的。
另外补了一条元测试：「模板切片必须覆盖到页面下半部分」，防止切片方式再退化。

> 教训：写"读文件做断言"的守卫时，**必须验证它在 bug 存在时会失败**。
> 一条永远为真的断言（或检查范围不对的断言）会让人以为已经守住了，
> 比完全没有守卫更糟 —— 本轮之前 §30.4 里那条 `assert(..., true)` 也是同一个病。
